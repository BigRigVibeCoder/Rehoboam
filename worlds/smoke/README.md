# The smoke world: golden runs, baselines and the bisect (SPR-008)

> **BLUF:** `smoke` is a world of seven dummy systems that touches every part of the engine determinism depends on, with two parallel scheduler levels every day. CI runs it for 1,000 sim-years on every PR and compares its plane-A hash ladder with the committed baseline. The nightly tier runs it monthly at 1, 2, 4 and N threads, three times each. Any divergence is bisected to its month, table, row and column.

## What is here

| Path | What |
|---|---|
| `systems/X*.odd.toml` | The ODD-R specs of the dummy systems (X-prefixed ids). They are **not** in `specs/systems` or the real Registry (SPR-008 ruling 2), and `rh-cli ownership` never sees them. |
| `registry_overlay.toml` | The ids of those systems, read only by the smoke tools (`lint_odd.py --overlay`, `gen_skeletons.py --overlay`, the runner's registration). |
| `baselines/smoke_yearly_1000y.ladder` | The golden baseline: seed 1, 1,000 years, a yearly ladder at 1 thread. Regenerated by `bin/regen_baseline.sh`, never typed. |

The code is `crates/rh-sys-smoke`: plane A, kind `system`, with the generated skeletons in `src/generated/`. The runner, the ladders and the bisect are in `crates/rh-golden`, which `rh-cli` exposes.

## The ladder format

Format `rehoboam-ladder v1` is documented normatively in `crates/rh-golden/src/ladder.rs`.

- **Header:** the world, seed, horizon, rung kind (`yearly` or `monthly`) and hash layout (`rehoboam/rh-snapshot/hash/v1`). There is **no** build id, wall time, thread count or host name. So ladders from two machines, two builds or two thread counts compare byte for byte. A run perturbed with the V-DET-11 hook adds `inject <month>:<table>:<row>`, so an injected ladder can never pass as a clean one. The header also names the input journal the history ran from (`journal <inputs> <head chain hash>`), and a run stopped before its horizon says so (`until <year>`).
- **Horizon:** `--years` is the history's horizon, because the synthetic inputs are those of the horizon. A run resumed from a keyframe must use its journal's own horizon: a shorter one is refused, and a longer one is refused unless `--extend` is given. `--until` stops a run early without changing its history; the bisect's resumed runs use it (VER-SPR-008 DEF-1).
- **Rungs:** one per year end or month end. Each holds:
  - its index, tick and date;
  - `state_hash`, the plane-A hash of the world tables and the engine-held tables;
  - `months`, the XXH3 of the month-end hashes the rung covers;
  - every table's Merkle root.
- **Failure:** a run that fails ends with a `failed` line.

```bash
target/release/rh-cli run smoke --years 1000 --threads 4 --ladder yearly --out a.ladder
target/release/rh-cli ladder compare a.ladder worlds/smoke/baselines/smoke_yearly_1000y.ladder
```

## Tiers

| Tier | What | Where |
|---|---|---|
| PR (`bin/check_all.sh`) | 1,000 years, yearly, at 1 thread and at N, each with at least 5% parallel levels. The two ladders must be identical and must equal the baseline. About 1 minute per run on a GitHub runner. | `Golden …` gates |
| PR, on a golden failure | `bin/golden_bisect_ci.sh`: builds the base revision and bisects it against the head. The report goes into the job's `check-report` artifact (`artifacts/bisect_report.txt`). | `ci.yml` |
| Nightly | 1,000 years, monthly, at 1, 2, 4 and N threads × 3 repeats, all identical (V-DET-01, V-DET-02: the G0 criterion), then V-DET-11 on 64 injected perturbations. The monthly ladder is uploaded as `golden-nightly-ladder`. | `bin/golden_nightly.sh`, `nightly.yml` |

## Baselines (SPR-008 ruling 6; `docs/13` §4.4)

- `bin/check_baseline.py` compares the committed baseline with CI's recomputation. In every case the baseline must equal the recomputation byte for byte, so it can only be regenerated, never typed. On top of that, the **C3 rule** fails closed (VER-SPR-008 MAJ-1):
  - **pull request:** the base branch is required (no base: exit 2). If the baseline changed against it, the PR title must end with a tag group holding `[C3]`. `SPR-008: golden CI [C3]` passes; `docs: explain the [C3] rule` does not. A title edit re-runs the gate.
  - **push:** if the baseline changed in `before..after`, a commit subject in that range must end with `[C3]`. A push with no previous commit (a new branch) reports the rule "not checked: no base".
  - **local run with no base:** reports "C3 rule not checked (no base ref)", never "unchanged".

  Controls in `bin/check_all.sh`: a hand-edited baseline fails; a regenerated one fails without the mark and passes with it (title and push forms); `[C3]` outside the trailing tag group fails; a pull request with no base fails closed.
- There is no merge queue (GitHub Free). The C3 PR's own **final commit** writes the new baseline with `bin/regen_baseline.sh`, and the commit subject must end with `[C3]`. The Architect merges it.
- A golden failure in a PR that is not C3 is never fixed by regenerating. Read the bisect report and explain the divergence: either an intended model change (declare C3) or a bug (fix it). See `docs/13` §4.5.

## What the golden run covers

The full engine loop, every phase and pulse, timers, lifecycle commands, events and material inputs through the journal (`crates/rh-sys-smoke/src/lib.rs` lists them per system). From the float zone (`rh-sample`) it covers **Poisson**, on both paths: inversion (mean 5, three regions) and PTRS (mean 12, one region; logs, `lgamma` and a variable number of draws; VER-SPR-008 MIN-1). The binomial, normal, gamma and beta samplers are not in the golden run; their golden vectors (V-DET-09) cover them.

## Parallel levels (VER-SPR-008 DEF-2)

A thread-count comparison only means something if some scheduler level holds two or more jobs, so that N threads actually split it. Every day, `X7.smoke_market` shares the Environment level with `X1.smoke_weather` and the Activity level with `X4.smoke_estate` (which exchanges `Settle` and `Audit` commands with it). That is 730 two-job levels a year, about 7% of the 10,319 levels the scheduler runs.

- **Evidence:** `rh-cli run smoke` prints a `dispatch:` line before its summary: levels run, levels with two or more jobs and their share, and the most jobs in a level. These figures describe the dispatch, not the history, so they are not in the ladder. They do not depend on the thread count.
- **Gate:** `--require-parallel 5` fails the run when no level holds two jobs or when the share is below 5%. The PR golden runs and the nightly runs use it.
- **Control:** `--leak-thread` (a test hook, like `--inject`) wraps X7 so that it adds a per-thread step counter to `market.ticks`. Its ladder header says `leak thread`. In `bin/check_all.sh`, the 1-versus-N comparison must FAIL with the leak and pass without it.
- **Daily, not hourly:** the engine spawns scoped threads for every level that holds two jobs. With X7 sharing the Hour pulse, a 100-year run at 4 threads took 150 s (about 25 minutes for 1,000 years). Daily, it takes 23 s. A persistent worker pool would remove that cost (to be filed as a backlog item).

## The bisect

```bash
target/release/rh-cli bisect --baseline <old rh-cli> --candidate <new rh-cli> --years 1000 --work target/bisect --out report.txt
```

1. It runs both builds yearly, with keyframes, to the first divergent year.
2. It resumes each build from its own keyframe of the latest permanent year before that year, through `rh_snapshot::resume`. This checks the keyframe's journal anchor, and skips ahead instead of re-running from year 0. Each build then runs monthly to the first divergent month.
3. It dumps both states there and compares table roots, then chunks (`first_divergence`), then rows.

The report names the year, the month, the tables that differ, the table, chunk, row and column, and both values. In the stub storage each column is its own table; for an engine-held table, the column is the first differing byte of the row. A spawned binary reads `worlds/smoke` from its own source tree, so a build of another revision runs that revision's world.

**V-DET-11** (`crates/rh-golden/tests/golden.rs`) checks this. The candidate is the same build with `--inject MONTH:TABLE:ROW`, which flips one row's low bit at a month end (a test hook, never used for a baseline). The bisect must name exactly that month, table and row:
- 4 seeded random cases in the PR tier, 64 nightly;
- 40 cases were checked by hand during the sprint.

## Cross-machine check (SPR-008 ruling 8; GOV-008 §1 D5; RUN-001; RUN-002 §4)

The G0 criterion is thread-count and repeat invariance (V-DET-01/02). The cross-machine evidence is recorded when the machines are available. In place of a cross-platform matrix, the different CPU vendors serve as the check (D5):
- a GitHub-hosted Ubuntu runner (the nightly reference);
- the director's laptop (Intel; RUN-001);
- `adjutant` (AMD; RUN-002), once per VM session before each gate from G0.

**Procedure** (about 10 minutes per machine, in one ~2-hour director session):

1. On the machine, check out the **same commit** as the nightly run whose ladder you compare against. Ladders only compare across machines for one source revision.
2. Download that run's `golden-nightly-ladder` artifact (GitHub → Actions → nightly → the run → Artifacts). Unzip it to get `smoke_monthly_1000y.ladder`.
3. Run `bin/cross_machine.sh smoke_monthly_1000y.ladder`. It:
   - builds the release `rh-cli` with the pinned toolchain;
   - runs 1,000 years monthly at 1 and N threads;
   - checks that the two runs agree and that they equal the reference;
   - writes `artifacts/cross_machine/<vendor>-<date>.txt`, recording the CPU model, vendor, thread counts, toolchain and both verdicts.
4. Exit 0 with `VERDICT: equal` is the evidence. Attach the `.txt` to the gate record (`docs/decisions-log.md`).
5. On a difference, the script's `ladder compare` line names the first differing month and its tables. The two monthly ladders, local and reference, are the evidence. The bisect needs both builds on one machine, so it cannot narrow a cross-machine divergence further. Treat the divergence as a **determinism leak** (`docs/13` §4.5 item 3): the queue freezes, and a WP is opened against R-03 with both ladders attached.
