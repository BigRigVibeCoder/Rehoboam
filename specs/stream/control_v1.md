## 0. What this is

The engine runs headless at the pace the director sets. `05.10` §3: "the engine's pace is a speed band (Live, 1 h/s … 1 decade/s) or MAX; pace never changes what happens, only how fast it happens." STR-5: "the engine's pace shall be set only by control commands, logged in the run log and never in the input journal." This document is the command: how a controller connects to the engine host, reads the pace, sets a band, pauses, resumes and advances the run to a tick, what the host answers, what it refuses, and what it writes where.

Four facts shape it and are not negotiable here (they are the ADRs' and the rulings'):

1. **The pace is host-side state, never history.** History is `f(engine_build, registry_version, manifest_hash, seed, input_journal)` (ADR-0006; CLAUDE.md). The band, the state and every command here live in the host's run loop, outside plane A: they are never journaled, never a record of channel A or C, never in a keyframe, and never in `state_hash`. A paused run writes no record and no keyframe (W35). A command here is therefore **not an input** and needs no acceptance cursor (A-36 is P2's, with the first journaled input on this socket).
2. **Pacing changes what is seen, never what happens.** A run paced through this socket, with any sequence of commands landing at any moment, produces the same channel-A bytes, the same `canonical_digest` per sealed year, the same keyframe set, the same ladder and the same journal as the headless run at `max` (V-STR-01 "at any pace"; `05.1` §4.4). The reference proves it on a simulated engine (§9) and SPR-027 T-03 proves it on `solo` (§11).
3. **The engine never waits on a controller** (`05.10` §7 item 3; PERF-5). The engine applies commands at its one decision point, before an instant (§3.3); a controller's answer waits for that, never the other way round; `control.status` never waits on the engine.
4. **`control.sock` carries the pace command and nothing else in v1.** Material inputs (tip and scheduled inputs, forks: STR-4) are P2.7's, over this same socket (D47). Their names, IF-3's (`05.9`), are reserved here and refused by name (§5.1); until they exist, nothing on this socket reaches plane A, and the read-only property of the stream sockets (`wire_v1.md` §4.5) extends to the control socket in v1 as a fact about the method table (§7).

IF-0 is three sockets in the run directory (`wire_v1.md` §0): `A.sock` and `C.sock` carry the stream, read-only in every version; `control.sock`, this document, is the one socket on which the world can be told anything, and in v1 it can be told only how fast to go.

## 1. Transport and permissions

| Item | v1 |
|---|---|
| Socket | A **Unix domain stream socket** (`SOCK_STREAM`) at `<run-dir>/stream/t<timeline_id, 10 digits>/control.sock`, beside `A.sock`, served by the **engine host** (the process that runs the engine's loop and `rh-stream`'s writer: `rh-cli run … --socket`), from the same module that serves `A.sock` (`crates/rh-cli/src/serve.rs`, the one file of `rh-cli` allowed a socket: `bin/lint_forbidden.py` `NETWORK_FILES`). The sifter never serves it (it has no pace). A fork, when forks exist (P2), has its own directory and its own control socket. |
| When it exists | Whenever the host serves its stream socket: `--socket` creates `A.sock` and `control.sock` together, before the first instant, and the host serves **both or neither**: the path check of `wire_v1.md` §1 (107 bytes) is made against the longer of the two paths, `control.sock`'s (six bytes longer than `A.sock`'s), so a run directory that fits the stream socket but not the control socket is refused before either is created, naming the path (C24). A headless run (no `--socket`) has no control socket and cannot be paused or paced after it starts; it is the run `bin/check_all.sh`'s golden gates and the performance baselines measure, and it pays nothing for this document (one load per instant in the loop, §6). |
| Start options | `--pace <band>` (default `max`) sets the band the host starts at; it is allowed without `--socket` (a run paced at `1y` feeding `rh-cli tail --wait` is legitimate). `--start paused` (default `running`; C8) starts the host held before its first instant; it is **refused without `--socket`**, because nothing could ever resume the run. Neither is ever read from the run log (§8.2). Every gate and baseline runs with neither, at `max`. |
| Platform | Linux (D5). Windows and macOS are out of scope in phase 1, as for the stream sockets. |
| Modes and ownership | The run directory is `0700`; `control.sock` is **`0600`** and belongs to the user running the host, like every socket of IF-0. The host holds an exclusive `flock` on `control.lock` beside the socket for its lifetime (the lock layout of `wire_v1.md` §1 and REV-SPR-026 R20: one lock file per served socket), so a second host for the same timeline cannot serve, a stale socket file after a crash is removed by the next host that holds the lock, and nobody unlinks a live socket. |
| Connections | Any number of **controllers**, each on its own connection, capped by the host (`too_many_controllers`, §5; default 8). Every connection may send every command: there is no owner, no lease and no lock on the pace (§7). The host numbers connections from 1 as it accepts them, and reads the peer's pid from `SO_PEERCRED`, for the run log (§8.1; C11). |
| Direction | Both sides send **CONTROL frames only** (§2). The host never sends a RECORDS frame on this socket; a RECORDS frame from either side is `invalid_frame`. A frame from a controller is at most 4 KiB, as a viewer's is on the stream sockets. |
| What reaches the engine thread | **One cell** (§3.3). A serving thread validates the request's shape, judges whether it changes the cell, queues it if it does, and answers when the engine has applied it; the engine's loop reads the queue at its decision point and never a socket. Nothing a controller sends is parsed on the engine thread. |
| Lifetime | The socket file is created before the first instant and unlinked at the end of the grace period after the run ends (§8.2); `A.sock`'s lifetime is exactly `wire_v1.md` §1's, and this document changes nothing about it (C15). A controller that cannot connect has no run to pace: it reads the sealed segments, or starts one. |

## 2. Framing and encodings: the wire's, reused

The control channel reuses `wire_v1.md`'s frame layer **as it is**, because a second framing would cost a second codec, a second fuzz corpus and a second conformance test for one more method table, and `wire_v1.md` §8 already fixes that this socket uses that framing:

- **Frames** (§2 there): the 12-byte header `RHWS`, `version` 1, `type` 1 (CONTROL), `flags` 0, `length`; a frame from a controller is at most 4 KiB and is judged on its header first; a RECORDS type (2) is `invalid_frame` **in both directions** on this socket (the stream's §2.2 sub-header never appears here); a nonzero flag, a bad magic, a length over the limit and a payload that does not decode are protocol errors, answered once with `id` null and then the connection is closed, exactly as there. **The close rule** (C16 as corrected, the wire's text winning over its round-1 reference): the host closes the connection after every answer whose `id` is null, because no request can be tied to it, and keeps it open after every answer that carries a request's `id`; §5 lists it per reason.
- **Canonical JSON** (§3.1 there): one JSON-RPC 2.0 object per frame, keys sorted, no whitespace, integers only (a float anywhere is `invalid_params`, R24), printable ASCII strings, depth at most 4, no repeated key, no unknown envelope member, no batch.
- **The error model** (§4.4 there): `{"code", "message", "data": {"reason", …}}`; the standard codes and the wire's −32110 and −32111 keep their numbers and meanings; this document adds codes in **−32120 to −32129** (§5), its own range inside IF-3's validation band, so that a code never means two things on two sockets of one run; every `method_not_found` from this socket carries `data.socket: "control"`, so a client that holds two sockets knows which one refused (C13).
- **The version rule** (§5 there): the frame header's `version` is the wire's; an unknown one is answered `unsupported_version` at v1 and closed. The **method set** has its own version string, `rehoboam/stream/control/v1`, reported by `control.status` (§4.1), whose `control` member (`format`, `version`) is **always present** in every control version, so a controller of any version learns from the one method every version has which method set it is talking to. Additive changes (a new result field, a new notification method) are minors and are not on the wire; a controller ignores a result field and a notification it does not know and the host never ignores anything (an unknown parameter is `invalid_params`, an unknown method `method_not_found`). What counts as a major change is the wire's §5 list, restated in the header above.

The values are the wire's too (§3.2 there): `tick` an `i64` of minutes, `seq` a `u64`, `timeline_id` a `u32`, `run_nonce` a `u64`, the history tuple's strings and digest, `band` and `state` tokens from the tables below. Wall-clock values appear in the run log only (§8.1), never on the wire.

**`rh-protocol`'s surface** (aligned to SPR-026's `control.rs` as built, PR #82; K7). The reason set and the −32601 message are **per socket**: the stream's dispatcher keeps the wire's eleven reasons and its read-only message; the control dispatcher adds this document's −32120 to −32122 reasons and answers −32601 with this socket's message and `data.socket: "control"`. The control dispatcher mirrors the stream's: `dispatch_control(&mut ControlConn, &dyn ControlHost, &[u8]) -> Reply { frames, close, used }` beside `dispatch(&mut Connection, &dyn Source, &[u8]) -> Reply`, in the crate's `control` module; `ControlHost` provides the published snapshot (§3.3), `submit` (a validated request onto its reply slot) and the wait on that slot. Three things SPR-026 built closed are what SPR-027 T-03 extends: `REASONS: [Reason; 11]` (the control reasons join it, or the table becomes per socket), `classify`'s code set (without the control codes, this document's error frames fail `decode_control`), and `MethodNotFound`'s fixed `READ_ONLY_MESSAGE` (the message becomes the socket's). The conformance test reads this document's golden file as it reads the wire's.

## 3. The pace: bands, states and the governor's rule

### 3.1 Bands (`05.1` §4.4)

The band is the rate of sim-time per wall-second. The tokens are those `stream.status.pace.band` already carries (`wire_v1.md` §4.1); the rates are integers derived from the world's calendar (`05.1` §4.1: `minutes_per_year`, 518,400 for a 360-day year, 525,600 for a 365-day one), so that the governor's arithmetic has no float and no rounding:

| Token | Meaning | Rate `r`, in sim-minutes per wall-second |
|---|---|---|
| `live` | real time: one sim-minute per wall-second, 60:1 (`05.1` §4.4 as amended by this PR, v1.16 at this writing; the street clock's 20–60:1 is the viewer's playback, `05.10` §3, not the engine's band) | 1 |
| `1h` | one sim-hour per wall-second | 60 |
| `1d` | one sim-day per wall-second | 1,440 |
| `1w` | one sim-week per wall-second | 10,080 |
| `1mo` | one sim-month per wall-second: a twelfth of the year (`05.1` §4.4 as amended by this PR) | `minutes_per_year / 12` (43,200 or 43,800) |
| `1y` | one sim-year per wall-second | `minutes_per_year` |
| `10y` | one sim-decade per wall-second | `10 × minutes_per_year` |
| `max` | as fast as the hardware allows: the governor never sleeps | ∞ (no rate) |

`1mo` is a twelfth of the year, not the current month's length, so that a band is one number for the whole run and a controller can predict the wall time of a tick. A host starts at `max` unless `--pace` says otherwise (§1); the default is `max` because every gate and every baseline runs headless at `max`, and a paced default would make the first run with a viewer attached look slow for no reason.

### 3.2 States

| Token | Meaning |
|---|---|
| `running` | The host advances the engine instant by instant, waiting between instants as the band says (§3.3). A pending **step** (§4.5) runs at `max` and ends in `paused` when its tick is reached. |
| `paused` | The host holds the engine between two instants: **the tip does not move**, no record and no keyframe are written (W35), and the journal is untouched. A seal already in flight off-thread when the pause landed may still land (`wire_v1.md` §6.1: a seal runs off the engine thread and completes on its own), which moves `sealed.last_seq` and may drop a year from the window under D42 (b); that is the stream's business and changes no record. Every command is still answered. A pause outlives the connection that issued it: the socket closing resumes nothing, and any controller may resume (§7; C14). A request a controller sent before closing is still applied (§7; L9). |
| `finished` | The run has ended, **in one critical section** (§3.3 item 5; K5): after the last instant's Bookkeeping the engine drained the queue (every request in it answered `run_finished`), dropped a pending step with no `step.reached`, set the cell to `finished` and published it; from then on every command is refused at submission (`run_finished`, §5) and `control.status` is answered until the host exits (§8.2 says when). The last year seals and `stream.end { reason: finished }` goes out on the stream socket. A host that stops on an error (`aborted`, `wire_v1.md` §4.3) is `finished` too, with `control.status.end` saying which. This is the one definition; §8.2 describes the exit around it. |

The state machine: `running` ⇄ `paused` (by `control.pause` and `control.resume`; a step reaching its tick is a pause the engine issues itself), and either → `finished` (the run's end or an abort, never a command). There is no transition out of `finished`. The host starts `running`, or `paused` under `--start paused` (§1).

### 3.3 The governor's rule (binding on the host, SPR-027 T-03)

**The cell and the queue.** The host keeps one cell, `(band, state, step_target: tick | null, anchor_tick, anchor_wall)`, and a **queue** of validated requests, each on its own **reply slot**. Serving threads write the queue under the host's lock; **only the engine's loop writes the cell**, at its one decision point (K2), and it publishes beside it a **snapshot** `(band, state, step_target, tip, next_seq, next_tick, end)` that `control.status` reads without waiting (K6). The tip is the tick of the last instant whose Bookkeeping ran (null before the first); `next_tick` is the agenda's next instant.

**The anchor** is the pair (the tip's tick, the monotonic clock) at the moment the **effective rate** last changed (K4): the effective rate is `max` while a step is pending and the band's rate otherwise, and no rate while paused, so a band change, a run-state change (a pause, a resume from paused, a step's end), and a step's start or clearing each re-anchor at (the tip, now), and nothing else does: a command that changes nothing, a band change while a step runs (the effective rate stays `max`), a pause that was already in force. Before the first instant the anchor's tick is the first instant's tick (`SimTime::EPOCH`, tick 0, in the engine; ticks may be negative, `05.1` §4.1; C9).

**The clock** is monotonic (Rust `Instant`); realtime appears only in the run log (§8.1). Deadline arithmetic is in `i128` nanoseconds and never overflows on any `i64` tick (C10). A deadline beyond `Instant`'s range (`Instant + Duration` would overflow) means **no deadline**: the host waits for a command, as it does when paused (K15).

**One decision point.** Only the engine makes decisions that depend on the tip, and it makes them at one point, **before** an instant. The loop, for the next instant at tick `t`:

1. **Decide, atomically.** The engine holds the host lock from taking the queue until it publishes (L1); equivalently, a request counts as queued until its slot is filled, and slots are released only after the publish, so a serving thread never sees an empty queue beside a stale snapshot. It takes the queue (every request landed since the last decision point, in arrival order) and applies each command to the cell (§4), resolving the checks that need the tip (`"instant"`, `past_tick`, a target already passed) against `next_tick` and the tip, and answering **every** queued command on its slot as it applies it, with the pace object **as the cell stands right after that command's own application**, in queue order (L2): `changed` true or false, or the refusal. A step whose target is already passed (no instant lies at or below it beyond the tip) is reached **inside its own application**: it is logged (`control.step:<T>` then `step.reached`) and answered `paused, step: null`. Then it re-checks a pending step: if `next_tick` is above the target (or there is no next instant), the last instant at or below the target has run, so it pauses now, re-anchors and writes `step.reached` (§8.1). A request landing in a step's reaching instant is therefore applied **first** and wins by construction: a resume clears the step and the run goes on; a pause is logged as `control.pause`, and no `step.reached` is written. It publishes the snapshot, and only then answers the `control.status` requests that were queued (behind their own connection's commands), with that published snapshot.
2. If `state = paused`, or there is no deadline: waits, by polling with a short sleep or on a wake a serving thread issues without waiting, until a request lands; then goes to item 1.
3. If the effective rate is a band's and the deadline `anchor_wall + ⌈(t − anchor_tick) × 10⁹ / r⌉` (`r` from §3.1; integers, rounded up) is still ahead: **waits until the deadline or until a request lands**, whichever is first. A request that lands during the wait ends it, and the engine goes to item 1 (so the request is applied before the instant, and a pause lands at once rather than one sleep later; Q8). A wait that reaches its deadline **runs the instant at once** (item 4), with no decision point at the deadline (L4), so a request landing exactly at the deadline lands during the instant (§9). A pending step has no deadline to wait for: it runs at `max`.
4. **Runs the instant** to the end of its Bookkeeping; the writer appends its records, and the tip moves, at its end. Requests landing meanwhile are queued, not applied: they are applied at the next item 1, which follows at once (a step has no wait, and at a band the governor's wait is the next instant's), so the delay is one instant's compute at most.
5. If the instant was the last, the run **finishes** in one critical section (K5, §8.2): the queue is drained with `run_finished`, a pending step is dropped with no `step.reached`, the cell says `finished`, and every later request is refused at submission. Otherwise item 1.

**Answers.** A request that **changes nothing against the published snapshot while the queue is empty and nothing of its connection is in flight** is answered at once by the serving thread, with `changed: false` and the published pace object; a `control.status` on a connection with nothing in flight is answered at once **from the published snapshot, whatever other connections have queued** (L3), and never waits on the engine: it waits only behind its own connection's earlier requests (L8). Every other request is queued and answered by the engine at item 1, with the tip and `next_seq` at which it took effect (C1): at most one instant's compute at `max`, immediate under a governor wait (item 3 is interruptible) or a pause (item 2), the genesis time before the first instant. The engine never waits on a controller. A paused tip is exactly the pause's answer's tip. A connection's requests are served **one at a time, in request order** (K3): a request behind an unanswered one on its connection is queued behind it, a `control.status` included, so a pipelined pair is answered in order and the second sees the first's effect.

Consequences a controller may rely on and the reference checks (§9):

- **An instant is never split.** A request that lands while an instant computes is applied after it, before the next one; one that lands during a wait ends the wait. So a `control.pause` answered with tip `t` holds the tip at `t` exactly, and `control.status.tip.tick` after a pause is the tick the answer carried.
- **Paused time is not owed.** A resume re-anchors at (the tip, now), so a run paused for an hour at `1y` does not race through the lost hour when resumed. For the same reason a band change does not race or lag: it starts fresh from the tip. And a step cleared by a resume re-anchors too: the next instant comes one band period after the clearing, not at the deadline the band would have computed from the anchor before the step (K4; the reference's `step-clear` scenario pins it: without the re-anchor an 810 ms stall on a 95 ms step, about ten seconds on a ten-year one).
- **A flood of requests that change nothing changes nothing**, the anchor included: a controller that re-sends `control.pace 1y` or `control.resume` every 50 ms, or every millisecond, at `1y` sees exactly the band's release times (C2; the reference's `starve-1y` and `starve-1mo` scenarios pin them to the nanosecond).
- **The band bounds the wall time from below, never from above.** At `1y` a sim-year takes at least one wall-second; on a world that simulates slower than the band it takes as long as it takes (the engine's speed is PERF budgets' business, `08` §1). The host measures nothing here and reports nothing here; the TUI shows the lag.
- **A step is a seek forward.** It runs unthrottled to its target whatever the band in force, then pauses; the band is kept and applies again from the next resume, which re-anchors. The alternative, a step at the band, would make one daily instant at `live` a 24-wall-minute wait on `solo` (ruling at round 1).
- **The waits are in the host's loop and in no plane-A crate.** The monotonic clock is read by `rh-golden`'s run loop (tool plane), never inside `rh-core`, `rh-snapshot` or any `rh-sys-*` (`bin/lint_forbidden.py`'s clock rule; SPR-027 T-03's lint line). Plane A has no notion that time passed.
- **Publish cadence is unchanged in v1.** `05.1` §4.4 says bands "change only the publish cadence and how far `advance_until` goes per wall interval"; the P1a writer appends after every instant at every band (one frame may hold one record at `live` and thousands at `max`, `wire_v1.md` §2.2), so v1 changes the second and leaves the first alone. A later version may coalesce publication at slow bands; nothing here prevents it and nothing in the records would show it.

## 4. Methods

The namespace on this socket is `control.*`. The requests of v1 are the five below; every other method, in any namespace, is `method_not_found` (§5), with a message that names what v1 accepts and, for a reserved name, why it is refused (§5.1). Requests carry an `id`; responses carry the same `id`, in request order per connection (a controller may pipeline); a notification or a response from a controller is `invalid_request`. The host sends no notification in v1 (what the alternative would add: §10).

Every command (§4.2 to §4.5) returns the same **pace object**, the state the engine applied and the tip at which it did (C1), so a controller never needs a second round trip to know the state it caused:

```json
{"band": "1y", "next_seq": 1234, "state": "running", "step": null, "tick": 216000}
```

| Field | Type | Meaning |
|---|---|---|
| `band` | token (§3.1) | The band in force after the command |
| `state` | token (§3.2) | The state after the command |
| `step` | `{"until_tick": i64}` \| `null` | The pending step's target, if a step is pending (§4.5) |
| `tick` | `i64` \| `null` | The tip at the decision point that applied the command: the tick of the last instant whose Bookkeeping had run (`null` before the first instant), the same number `stream.status.tip.tick` on `A.sock` reports at that moment (C26, L6) |
| `next_seq` | `u64` | Channel A's next seq at that moment (`stream.status.tip.next_seq`), so a controller can confirm that nothing was written while paused: the same number at the pause and at the resume |

A command is **accepted** when it is well-formed and the state admits it. An accepted command that **changes the cell** is applied by the engine at its decision point (§3.3), appends exactly one run-log line (§8; a step whose target is reached at once also appends its `step.reached` line, §4.5), and is answered with the pace object and `changed: true`. An accepted command whose effect is already in force (`control.pause` while paused, `control.pace` to the band in force, `control.resume` while running with no step pending, `control.step` to the target already pending) **changes nothing**: it is answered with `changed: false`, re-anchors nothing and is not logged (C2), so that a controller's commands are idempotent and a flood of them is harmless. Whether it changes anything is judged by the engine at application against the cell as the queue left it, except that a serving thread answers it **at once from the published snapshot when the queue is empty and nothing of its connection is in flight** (K3); a command queued behind others is judged, and answered, by the engine in order, so a second controller's pause behind a first's is answered `paused, changed: false`, a second step to the target a first is setting is answered `changed: false` with that target shown, and a connection that pipelines two pauses has them answered in request order. A **refused** request (§5) changes nothing either: no cell write, no run-log line, no anchor reset.

### 4.1 `control.status`

Request: `{"id": 1, "jsonrpc": "2.0", "method": "control.status"}` (`params` absent or `{}`; any member is `invalid_params`). Accepted in every state, logged never (a read), answered after the run ended too, and **never waits on the engine**: it reads the snapshot the engine published at its last decision point (§3.3; K6), whatever other connections have queued (L3). It waits only behind its own connection's earlier requests (L8): queued behind a command of its own connection, it is answered after the publish that applied that command, with the published snapshot (L2).

Result, from one snapshot, so that `tip` and `pace` agree:

| Field | Type | Meaning |
|---|---|---|
| `control` | `{"format": "rehoboam/stream/control/v1", "version": 1}` | This document. **Always present in every control version**, so a controller learns the method set from the one method every version has (C18) |
| `timeline_id` | `u32` | The timeline this socket controls (P1a: 0) |
| `run_nonce` | `u64` | This host's start (`wire_v1.md` §3.2): a controller that reconnects and finds another nonce with the same `history` is talking to a resumed host, whose pace is the start pace again (§8); another `history` is another run |
| `history` | `{"engine_build", "registry_version", "manifest_hash", "world_seed"}` | The history tuple (`wire_v1.md` §4.1). The pace is not in it |
| `calendar` | `{"minutes_per_year": int}` | The year, so a controller computes a band's rate (§3.1) and a date's tick |
| `pace` | the pace object | `band`, `state`, `step`, `tick`, `next_seq` as above, from the published snapshot |
| `tip` | `{"tick": i64 \| null, "next_seq": u64}` | The stream's tip (`wire_v1.md` §4.1), the same numbers as `pace.tick` and `pace.next_seq` |
| `end` | `{"reason": "finished" \| "aborted"}` \| `null` | Null while the run goes on; the reason when `state = finished` (the stream's `stream.end.reason`) |
| `controllers` | `int ≥ 1` | Connections open on this socket, this one included (§7) |

Invariants the reference checks, against the published snapshot (so they hold for a status read while an instant computes: the tip is the last decision point's, and a pending step's target is above it): `pace.tick = tip.tick`; `pace.next_seq = tip.next_seq`; `state = finished` ⇔ `end ≠ null`; `step ≠ null` ⇒ `state = running` and `step.until_tick > tip.tick`.

### 4.2 `control.pace`

Request: `{"id": 2, "jsonrpc": "2.0", "method": "control.pace", "params": {"band": "1y"}}`.

- `params` is exactly `{band}`; `band` is one of the eight tokens of §3.1. A missing or extra member, a non-string, an unknown token (`"1yr"`, `"MAX"`, `"1 y"`) or a float anywhere is `invalid_params`, with `data.detail` naming the member.
- Accepted in `running` and `paused`: the band changes, the state does not (a band set while paused takes effect at the resume; a band set while a step runs takes effect after the step), the anchor is reset, a pending step stays pending. Refused in `finished` with `run_finished`. To the band in force: `changed: false`, nothing else.

Result: the pace object plus `"changed": bool`.

### 4.3 `control.pause`

Request: `{"id": 3, "jsonrpc": "2.0", "method": "control.pause"}` (no params).

- Accepted in `running`: the state becomes `paused` at the engine's next decision point (§3.3: the instant in progress, if any, completes and its records are written; then the tip holds, and the answer's `tick` is that tip). A pending step is cleared (the pause is the controller's, now; `step` is null in the result). In `paused`: `changed: false`. Refused in `finished` with `run_finished`.
- **What a pause does not do** (W35; `05.10` §4's "keyframe markers at auto-pauses" is P2's Time-Machine, not this): it writes no record of any kind on any channel, no keyframe, no journal row, and no segment is sealed by it. A year completed before the pause seals on its own schedule, off-thread, as it would have (C7). The pause probe (§11) asserts exactly four things: no record, no keyframe, no journal row, and `next_seq` unchanged from the pause's answer to the resume's; the only seals it allows are of years completed before the pause.

Result: the pace object plus `changed`.

### 4.4 `control.resume`

Request: `{"id": 4, "jsonrpc": "2.0", "method": "control.resume"}` (no params).

- Accepted in `paused`: the state becomes `running` at the band in force, the anchor is reset to (the tip, now), so no paused time is owed. In `running` with no step pending: `changed: false`. In `running` with a step pending, `control.resume` **clears the step** (the run goes on past the target, at the band) and reports `changed: true` with `step: null`; the effective rate changed (from `max` back to the band), so it re-anchors at (the tip, now) and the next instant comes one band period later (K4). Refused in `finished` with `run_finished`.

Result: the pace object plus `changed`.

### 4.5 `control.step`: advance to a tick

Request: `{"id": 5, "jsonrpc": "2.0", "method": "control.step", "params": {"until": {"tick": 432000}}}` or `"until": "instant"`.

- `params` is exactly `{until}`; `until` is `{"tick": i64}` (advance to tick `T`) or the string `"instant"` (advance one instant: `T` is the tick of the next instant, which the engine knows and the controller does not; it is resolved at application, against the agenda's `next_tick` at that moment). Anything else is `invalid_params`.
- **Meaning (W37):** the engine runs **at `max`** (§3.3: a step is a seek forward) until **after Bookkeeping of the last instant whose tick is at or below `T`**, then pauses. When `T` is an instant's tick, that is the state after Bookkeeping of `T`: the state a `STEP_DIGEST` at `T` hashes (`channel_a_v0.sql`: "once per Month pulse, after Bookkeeping") and the state `rh_golden::materialize(run_dir, T)` rebuilds (SPR-027 T-02). When `T` falls between two instants, the engine pauses after the earlier one and `pace.tick < T`; a controller that wants an exact tick names an instant (a day start, in P1a) or reads `pace.tick` from `control.status` once paused.
- Accepted in `paused` and `running`: the state becomes (or stays) `running`, the step's target is set (a second `control.step` **replaces** a pending target; the result shows the one in force; to the target already pending: `changed: false`), and the anchor is reset at a step's start (the effective rate becomes `max`; a replacement changes no rate and does not re-anchor). When no instant lies at or below `T` beyond the tip (`T` is between the tip and `next_tick`), the target is reached at once: the command is accepted, logged (`control.step:<T>` then `step.reached`, §8), and the result already shows `state: paused`, `step: null`.
- Refused: `past_tick` when `T` is at or below the tip (`T ≤ pace.tick`) or, before the first instant, when `T` is **below the first instant's tick** (C9; a step to the first instant's own tick runs it): the step is not an input and cannot fork, so a tick in the past is simply not somewhere a run can advance to (ADR-0025 §5 is about inputs; a controller that wants the state at a past tick materializes it, `05.10` §4); `run_finished` in `finished`, or when the run finishes before the step is applied (C14, K5).
- When the target is reached the engine itself pauses at its decision point (§3.3 item 1) and logs it (§8); the controller sees it as `state: paused` and `step: null` in `control.status`, with `pace.tick` the tick reached. **The host sends no notification**: a controller polls `control.status` (a read of the published snapshot, cheap at any rate), which keeps v1 to requests and responses. A `control.reached` notification is the additive change a later minor would make (§10).

Result: the pace object (`state: running`, `step: {until_tick: T}` with `T` resolved for `"instant"`; or `paused` with `step: null` when reached at once) plus `changed`.

### 4.6 Worked sequence

A controller that wants to watch year 10 at one sim-day per second and then let the run go:

```text
control.status                        -> pace {band: max, state: running, step: null, tick: 4665600, next_seq: 8112}
control.step {until: {tick: 5184000}} -> pace {band: max, state: running, step: {until_tick: 5184000}, tick: 4665600, next_seq: 8112}, changed true
  (poll) control.status               -> pace {band: max, state: paused, step: null, tick: 5184000, next_seq: 9001}   # after Bookkeeping of 5184000
control.pace {band: 1d}               -> pace {band: 1d, state: paused, step: null, tick: 5184000, next_seq: 9001}, changed true
control.resume                        -> pace {band: 1d, state: running, step: null, tick: 5184000, next_seq: 9001}, changed true
  … 360 wall-seconds later, year 11 begins …
control.pace {band: max}              -> pace {band: max, state: running, step: null, tick: 5702400, next_seq: 9988}, changed true
```

The run log then holds four `pace` lines for the commands and one for `step.reached` (§8); channel A holds exactly the records the headless run holds, at the same seqs, with the same digests (§9).

## 5. Refusals

A refused request is answered with an error response carrying the request's `id` (or `null` where the wire says so) and **changes nothing**: no cell write, no run-log line, no anchor reset, no effect on any other connection. The wire's codes keep their numbers and meanings; this socket's own reasons take −32120 to −32129. The "connection" column says what the host does with the connection after the answer (C16, as the Architect corrected it on SPR-026's finding that `wire_v1.md`'s text and its round-1 reference disagreed; the text wins and SPR-026 fixes the wire reference): **every answer whose `id` is null closes the connection**, since nothing on it can be tied to a request (`invalid_frame`, `unsupported_version`, `too_many_controllers`, `parse_error`, and an `invalid_request` or `invalid_params` the host could not attach to a request: a batch, an unknown envelope member, a notification from a controller, a float the parser caught); **every answer that carries the request's `id` keeps it open** (`method_not_found`, an `invalid_params` on a well-formed request, `past_tick`, `run_finished`). The reference's dispatch cases hold one of each class, and the self-test asserts the connection's state after every one.

| Code | `reason` | Extra `data` fields | When | Connection |
|---|---|---|---|---|
| −32700 | `parse_error` | `"detail"` | The payload is not JSON, or exceeds the parser (`wire_v1.md` §4.4); `id` null | **closed** |
| −32600 | `invalid_request` | `"detail"` | Not a JSON-RPC 2.0 request object; a batch; an unknown envelope member; a non-ASCII string; a notification or a response from a controller; `id` null | **closed** |

| −32602 | `invalid_params` | `"detail"` | A parameter missing, of the wrong type, out of range or unknown; an unknown band token; a member in the params of a method that takes none (the request's `id`); a float anywhere in the payload, which the parser refuses before any request is read (R24; `id` null) | kept open with the request's `id`; **closed** with `id` null |

## 6. What the engine sees

Nothing. Normative, for SPR-027 T-03 and every later version:

- **Plane A is untouched.** `rh-core`, `rh-events`, `rh-snapshot`, `rh-stream` and every `rh-sys-*` crate have no type, no field and no function for the pace. The cell, the queue and the governor are in `rh-golden`'s run loop (tool plane), the socket in `serve.rs`, the method table in `rh-protocol` (tool plane, a leaf). `bin/lint_arch.py`'s plane-A closure and `bin/lint_forbidden.py`'s `network`, `network-reexport` and clock rules hold as they are; SPR-027 adds no escape.
- **The pace is in no hash.** `state_hash` covers plane-A state (`05.1` §6; SPR-007); the cell is not plane-A state. The reference's planted control `band-in-hash` mixes the band into the digest and must FAIL pace invariance (§9).
- **The pace is in no record and no keyframe.** Channel A's kinds are `channel_a_v0.sql`'s; none is a pace. A keyframe is written when `05.1` §4.2's Bookkeeping trigger says (every 10 sim-years) and never because the run paused (W35). The reference's `pause-writes-record` control appends a line at a pause and must FAIL.
- **The pace is not an input.** The journal (`rh-snapshot` `journal.rs`; IF-2) gains no row from this socket in v1; its row count and chain head are the same after any command sequence (SPR-027 T-03's test). The reference's `pace-in-journal` control journals a band change and must FAIL.
- **One load per instant.** The headless cost of the governor is the read of one cell before each instant and a comparison; V-PERF-04 and V-PERF-11 (instructions and allocations per steady-state tick at `max` with no socket) are unchanged (SPR-027 T-03's acceptance).
- **No socket on the tick path.** The serving threads of this socket write the queue under the host's lock and never touch the writer, the window or the engine; the engine's loop reads the queue and the cell and never a socket. "The engine never waits for a reader" (`wire_v1.md` §0 fact 1) becomes here "the engine never waits for a controller": it waits at a pause because it was told to, which is the point, and for nothing else.

## 7. Concurrency: many controllers, one cell, last write wins

- **A serving thread reads to EOF** and submits every complete request frame it received (L9); those requests are applied whether or not the peer is still there, and the answers to a closed peer are dropped. A partial frame at EOF is discarded. So a one-shot tool that sends `control.pause` and closes gets its pause, and a pause outlives its connection (§3.2).
- **Any connection may command.** The socket is `0600`, so every controller is the one user, and the engine applies commands in arrival order: the cell holds the last applied command, and the run log holds every change in that order (§8). A second controller gets the same methods and the same answers as the first; `control.status.controllers` tells it how many there are. There is no owner, no lease, no `control_held` error. **One controller's `control.step` or `control.resume` un-pauses another controller's pause**, and a pause outlives the connection that issued it (C14): closing a connection changes nothing.
- **Why not one controller at a time.** The P1a controllers are short-lived tools: `rh-cli pace <run-dir> <band>`, `rh-cli pause <run-dir>`, `rh-cli resume <run-dir>`, `rh-cli step <run-dir> --tick T` (each one connection, one request, one answer, exit) and, later, a long-lived harness (`rh-tui`, P2.7; `rh-view`, ADR-0036). A lease would make the one-shot tools fail whenever the harness is open, for no safety gained: the pace is not history, a wrong band costs nothing, and the run log says who asked what (the connection number and the peer pid, §8.1). The alternative is §10's.
- **Ordering.** Commands from one connection are applied in request order; commands from two connections are applied in the order the host's lock admits them to the queue, and each answer reports the state its own command left. A controller that reads `control.status` after another controller's command was answered sees that command's effect (one cell, one snapshot).
- **The method table is the read-only property, inverted.** A conformance test enumerates the method table of every control version: v1's is exactly `{control.status, control.pace, control.pause, control.resume, control.step}`, and the stream sockets' tables never gain a `control.*` entry (`wire_v1.md` §4.5's invariant; SPR-026's planted control "a dispatcher with a fourth method (`stream.pace`)" and this document's `pace-on-stream` and `extra-method` controls all fail by name; C20). The two tables are disjoint for every version of both.
- **The cap.** `too_many_controllers` at the host's cap (default 8, a host setting) bounds serving threads, as `too_many_viewers` does on the stream sockets, and is retriable.

## 8. The run log; writer exit, kill and resume

### 8.1 `<run-dir>/run.log`

The host appends one line per command that **changed the cell** (§4; a no-change command is not logged, C2) to `<run-dir>/run.log` (`05.10` §7 item 4: "logged in the run log, never in the input journal"; STR-5), a text file in the run directory beside `run.toml`, LF-terminated, ASCII, append-only across the life of the run and across resumes:

```text
pace <wall_ns> <band> <state> <tick> <method> <run_nonce> conn=<N|-> pid=<P|->
host <wall_ns> <event> <tick> <run_nonce>
```

| Line | Fields |
|---|---|
| `pace` | `wall_ns`: the host's realtime clock in integer nanoseconds since the Unix epoch when the engine applied the command (host-side only; never on the wire, never in plane A; the governor itself runs on the monotonic clock, C10); `band` and `state`: the pace **after** the command (so the line says what the run is doing from here); `tick`: the tip at the command (`~` before the first instant); `method`: `control.pace`, `control.pause`, `control.resume`, `control.step:<until_tick>` (the resolved target), `step.reached` for the pause the engine issues itself at a step's target (§3.3), `host.start` for the start pace, or `host.resume` for a resumed host's start pace (§8.2); `run_nonce`: the host's; `conn=N`: the connection's number, a per-host counter from 1 in order of acceptance, or `-` for a line the engine wrote (`step.reached`, `host.start`, `host.resume`); `pid=P`: the peer's pid from `SO_PEERCRED`, or `-` when the platform gives none or the line is the engine's (C11) |
| `host` | `event`: `start` (the host began serving, with the start band and state in a `pace … host.start` line that follows at once), `finish`, `abort` (`wire_v1.md` §4.3's reasons) or `resume` (a host that started from a keyframe, §8.2, followed at once by its `pace … host.resume` line); `tick`: the tip at the event: `~` at a fresh start, the keyframe's tick at a resume, the last instant's tick at a finish |

The first two lines of a fresh run are therefore `host … start ~ <nonce>` and `pace … max running ~ host.start <nonce> conn=- pid=-` (the start band; `control.status` would answer the same). A refused request writes no line. A no-change command writes no line. `control.status` writes no line.

**What the run log is not.** It is not part of history: `history = f(build, registry, manifest, seed, journal)` does not read it; `rh-cli replay`, `rh_golden::materialize` and `rh-cli tail` never open it; a run directory with it deleted replays and materializes to the same hashes. It is not in any hash and not in any segment. It is a record for people (the director reading why year 300 took an hour, and who asked) and for SPR-027 T-03's probe (which asserts one `pace` line per change and none per refusal or no-change command). The read-only test (SPR-013 T-10's form) excludes it from nothing: `tail` and `materialize` do not write it, and the host is the only writer; a test that diffs the run directory's tree after a `tail` sees the same `run.log` bytes it saw before.

**Its format is this document's.** The line above (the W30 row's `pace <wall_ns> <band> <state>` with the tip, the method, the nonce and the controller's identity appended: Q2, C11) is versioned with the method set; a change to it is a change to this document.

### 8.2 Writer exit, kill and resume

| Event | What the host does | What a controller sees |
|---|---|---|
| **Normal end** (the horizon reached) | A pause before the last instant holds the run; once the last instant's Bookkeeping has run, **finishing is never held** (C14), and it happens **in one critical section** (K5): the queue is drained and every request in it answered `run_finished`, a pending step is cleared with no `step.reached`, the cell says `finished`, and every later request is refused at submission, so no request falls between the last drain and the end unanswered; then the last seal lands, `stream.end { finished }` goes out on the stream socket, `host … finish` is logged, `state = finished` in the cell. The host then answers `control.status` and refuses the four commands with `run_finished` for a **grace period** on `control.sock` only (a host setting; default 2 seconds), which **ends early when no controller is connected** (C15), so that a controller that polls sees `finished` rather than a closed socket and an unattended host does not linger; then it unlinks `control.sock`, releases its lock and exits. `A.sock`'s end-of-run lifetime is exactly `wire_v1.md` §1's and is not changed by this | `control.status.pace.state = finished`, `end.reason = finished`; then the connection closes |
| **Abort** (a poisoned engine, BCK-002 A-42; `wire_v1.md` §6.2) | As above with `aborted`: no partial seal, `stream.end { aborted }`, `host … abort`, the grace period, exit | `state = finished`, `end.reason = aborted`, `run_finished { end: aborted }` |
| **`kill -9`** | Nothing: the socket file and the lock file stay on disk, the lock is released by the kernel, the run log ends where it ended (its last line may be the last applied change; a line is written whole or not at all: the host writes each line with one `write` of the full line and `fsync`s nothing, so a torn line is impossible and a lost line possible, and neither matters to history) | The connection closes without a frame. A controller that reconnects fails to connect (no host) until a host resumes |
| **Resume** (`rh-cli run <world> --run-dir D --resume K [--socket] [--pace <band>] [--start paused]`, with `K` the keyframe the resumed run starts from: SPR-013 T-09's line, `wire_v1.md` §6.2's resumed host; C25) | A new `run_nonce`; the stale socket files are removed under the locks and new ones created; **the pace starts again at the command line's band (default `max`) and state (default `running`; `--start paused` holds the resumed host before its first instant)**: the pace was never state, so there is nothing to restore, and the run log is never read back (a host setting the band from a log line would make the log an input to the host's behaviour, which it is not; the controller that paused the old host sets the new one, or starts it held). The run log gains `host … resume <K's tick> <new nonce>` and `pace … <band> <state> <K's tick> host.resume <new nonce> conn=- pid=-`, after the old lines; the resumed host's first instant is the one after the keyframe's (`rh-golden` `run.rs`), and it re-emits the lost year's records as the same bytes (`wire_v1.md` §6.2), at whatever pace it is now told | A controller that reconnects reads `control.status`: a new `run_nonce` with the same `history` is the resumed host, at the start pace; it sets the band again if it wants one. A different `history` is another run |

A pause therefore does not survive a kill, and a director who needs a run held across a restart resumes it with `--start paused`. What changes under the alternative (restore the band from the log): §10.

## 9. The reference, the golden file and the controls

`specs/stream/selftest_control_v1.py` (standard library only; it loads `selftest_wire_v1.py` by path for the frame codec, the canonical JSON, the request and error builders and the stream's method table, and `canonical_v0.py` through it) is the independent reference `rh-protocol`'s control dispatcher and `rh-golden`'s governor must agree with. It holds:

1. **The method table and the dispatcher.** `METHODS` is exactly the five methods of §4; `RESERVED` is §5.1's table; `Host` validates a request on the serving thread's side (`submit`), queues it on its own slot, and applies the queue at the engine's decision point (`before_instant`; `after_instant` only finishes the run after the last instant; C1, K2), answering every request of §4 and every refusal of §5. A check asserts the table, the disjointness from the wire's `METHODS`, the detail of every reserved name against §5.1's table typed out independently, `data.socket` on every `method_not_found`, and that no accepted command's name is in `RESERVED`.
2. **The simulated engine.** `Engine` is a deterministic record generator: instants at fixed ticks from the epoch (tick 0 is the first; months of a 360-day year, 12 per sim-year, four years), each emitting a fixed number of canonical-shaped lines derived from the tick alone, a `STEP_DIGEST` whose `state_hash` is a hash of the state so far at each year's end, a `KEYFRAME` every two years (the simulation's cadence; the engine's is ten), a journal with one row before the run, and a ladder of per-year hashes. It knows nothing of the pace: `Engine.run_instant()` takes no honest argument (the `band-in-hash` control is the one caller that passes it one). Each instant takes 10 ms of the fake clock, its records land, and the tip moves, at its **end** (K1), so a command can land while an instant computes and be applied after it. **The delivery rule** (ties included): at a decision point at time `now`, every command with `at_ns ≤ now` is delivered and applied before the instant; a governor wait is cut by a command with `at_ns < deadline`, which is then delivered at a new decision point; a command with `release ≤ at_ns < release + 10 ms` lands while the instant computes, one at exactly `release + 10 ms` lands after the instant's records and before the decision point (a status then still reads the snapshot published before the instant; L3), and both are applied at the decision point after the instant; so a command at exactly the release time the engine waited for lands during the instant, and at `max`, where the engine never waits, a command at exactly a decision point's time is applied before that instant.
3. **The governor** (§3.3) over a `FakeClock` whose `sleep_until` advances it, so that the rule's arithmetic (integers only), the anchor resets on every change of the effective rate, the interruptible wait and the one decision point are exercised exactly, with the wall time at which each instant started recorded.
4. **Pace invariance.** The same engine is run headless at `max` and under thirteen scripted command sequences: `1y` throughout; `10y`; a pause of two wall-seconds after year 1 and a resume, with `control.status` read inside the pause; a pause before the first instant, a step to a tick between two instants, a band change while paused, a step of one instant, a step to a later tick and a resume; two controllers interleaving band changes, a pause, a resume and a step; a step contested by a second controller that pauses it, resumes, steps again and replaces the target while it runs (C3); commands landing **while an instant computes** (K1): a pause in instant 0, a resume, a pause and a no-change `control.pace` each landing in a step's **reaching instant**, a status read mid-instant, and a pause at exactly a decision point's time; a flood of `control.resume`, `control.pace 1y` and `control.status` every 50 ms at `1y` and a `control.resume` every 0.9 s at `1mo` (C2); a host started with `--start paused` (C8); a step started while running at `1y` and cleared by a resume 95 ms later (K4); a step beyond the horizon with a pause landing in the last instant (K5); and the queue fold (K3, L1–L3): two controllers' pauses in one instant, two identical steps, a pipelined pair of pauses on one connection, two steps `"instant"` behind one another, a pause and an opposite resume landing in one instant, a pipelined (pause, status) pair with unsorted ids, a step reached inside its own application with a status queued behind it, and a status at an instant's end while another controller's pause is queued. The check asserts: the concatenated channel-A lines are byte-identical; the per-year digests are equal; the keyframe set is the same; the journal is unchanged (row count and chain head); the ladder is identical; **and** that the governor really slept (at `1y` and `1mo` every instant started exactly at the band's deadline, to the nanosecond, floods included; at `max` the clock moved only by the instants' own compute), that the pause really held the tip (no instant ran between the pause and the resume, `next_seq` and `tick` equal in the pause's answer, the status read inside it and the resume's answer), that the resume owed no paused time (the first instant after it exactly at its deadline from the tip at the resume), that each step paused exactly after Bookkeeping of the last instant at or below its target, that the contested step's targets were the ones the commands left, that a resume or a pause landing in a step's reaching instant won (the resume's answer `running` with no step and the cell `running`; the pause logged as `control.pause` with no `step.reached`), that a no-change command landing there was answered at once from the published snapshot, that a status read mid-instant showed the published snapshot with its step target above its tip, that the clearing resume's next instant came exactly one band period after it, that the pause landing in the last instant was answered `run_finished` with no `step.reached` and no `control.pause` logged, that the queue-fold answers are `paused, changed: false` behind a pause, `changed: false` with the target shown behind an identical step, in arrival order on one connection (by the host's answer counter, with ids that are not sorted), `running, changed: true` for a resume opposite a pause in one instant with the cell ending `running`, `paused` for a status pipelined behind a pause, `paused, step: null` for a step reached inside its own application and for the status queued behind it, and the published tip (not the live one) for a status at an instant's end, and that every engine-written line (`host.start`, `step.reached`) carries `conn=- pid=-` (K10).
5. **The run log** rendered by the host for each sequence: one `pace` line per change, none per refusal, no-change command or read, the `host` lines, in order; compared with the golden `scenario` lines.
6. **Refusals:** every reason of §5 produced by a planted request, with whether the connection closed (one case of each class: `id` null closes, a request's `id` keeps it open); every reserved name; a RECORDS frame; a 5 KiB frame; a float band; an unknown band; an extra member; `control.step` to the tip, to the past and to below the first instant; the four commands after `finished`.
7. **The golden file** `specs/stream/golden/control_v1.txt`: `frame <name> <hex>` with its decoded `control <canonical json>` line for one frame of every request, result and error; `dispatch <name> <request hex> <reply hex>` for every planted request on a fresh connection to an idle host at a known tip (the engine run to year 1; the `_finished` cases on a finished host, the `_with_step` cases with a step pending, the `_genesis` and `_before_first` cases before the first instant); `scenario <name>` followed by `clock <wall_ns> <tick> <k>` lines (when each instant started), `answer <at_ns> <conn> <method> …` lines (what each scripted request was answered, `control.status` reads included: the applied band, state, target, tip, `next_seq` and `changed`, or the published snapshot for a status, or the refusal's reason) and `log <run-log line>` lines for each sequence; and `invariance <sha256 of the channel-A lines> <keyframe ticks> <journal head> <last ladder hash>` once, the value every sequence reproduced. `rh-protocol`'s conformance test reproduces every `frame` and `dispatch` line; SPR-027 T-03's governor test reproduces the `clock` and `answer` lines of each scenario on the same fake clock.
