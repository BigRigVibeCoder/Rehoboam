## 1. Scope

`rh-core` and the system crates own all of **plane A** (authoritative state; ADR-0024) and its evolution:
- terrain and fields;
- the region graph;
- the ledger of living persons;
- the life-course log;
- pop aggregates;
- named actors;
- polities, armies and markets;
- the scheduler (agenda and timers), RNG, invariants and event emission.

`rh-core` has **no I/O**. Every host (CLI, server, Python wheel, optional GDExtension) wraps the same library. Plane-A code never reads planes B or C.

## 2. The `SystemModel` contract and ownership rules

Every simulation system implements one trait. A new system or fidelity level is a new implementation of the trait plus Registry entries (success criterion S4).

**Every implementation has an ODD-R spec** (`docs/templates/system_spec_odd_r.md`). ODD-R is the ODD protocol for simulation models (Grimm et al. 2010, 2020; R12 §15) adapted to this contract. One filled spec per system per fidelity level lives at `docs/05_architecture/systems/<SYS.id>_F<n>.md`. The trait maps onto it one to one:
- `descriptor` → the header;
- `access` → §2, plus §3 commands and lags;
- `schedule` → §3;
- `params_schema` → §7.0;
- `step` → the §3 pseudo-code and §7;
- `invariants` → §7.x and §9;
- `declared_aggregates` → §4.11 and §1.

A later lint diffs `AccessSpec` against the spec's §2 tables. ODD's documented failure modes are ambiguous scheduling, parameters confused with inputs, and specs describing the intended model rather than the program. They are exactly the agent risks for determinism, so the template targets them explicitly.

```rust
/// Frozen in rh-core (SPR-005; crates/rh-core/src/system.rs).
pub trait SystemModel: Send + Sync {
    fn descriptor(&self) -> SystemDescriptor;            // "M2.demography", fidelity "F1", spec version
    fn access(&self) -> AccessSpec;                      // reads: column, owner, lag; writes: OWNED columns and their plane
                                                         // commands sent (with their owner) and applied; event kinds emitted (SPR-006)
    fn schedule(&self) -> Vec<PulseBinding>;             // (pulse, phase), e.g. [(Month, Vital), (Day, Agenda)]
    fn rng_purposes(&self) -> Vec<&'static str>;         // the generated RngPurpose names; checked against [[rng]] at registration
    fn params_schema(&self) -> ParamSchema;              // exported to the Registry / JSON Schema
    fn step(&self, binding: PulseBinding, world: &mut SystemView<'_>, ctx: &mut StepCtx<'_>) -> Result<(), SimError>;
    fn invariants(&self, world: &WorldTables) -> Vec<InvariantResult>;
    fn declared_aggregates(&self) -> Vec<AggregateSpec>; // targets for stylized facts + conserved quantities
}
```

`step` receives the whole `PulseBinding`, not only the pulse, because a system may bind one pulse in two phases (S6 and S7 bind `Day` in both `Vital` and `Agenda`) and must know which one is running. It sees the world through a `SystemView`, which enforces the system's `AccessSpec` at run time: a read of an undeclared column or a write to a column the system does not own is a `SimError`, and lagged reads see the start-of-instant value.

**Rules for systems** (RT-M11; enforced by lints and the scheduler at startup):

1. **Single-writer column ownership.** Every column and relation has exactly one owning system, declared in the Registry with units and meaning. Other systems read it through **contract crates**: types and accessors only, no implementation.
2. **Lifecycle command queues.** Births, deaths, migrations, transfers of office or property, and infection-state changes are submitted as **typed commands** to queues owned by `rh-core`. The owner applies them in `(phase, PersonId)` order (SPR-006: the queue key is `(tick, phase, PersonId, seq)`; the owner receives its queue when it next runs). Each command has one owner, declared in its `AccessSpec` (`applies`) and named by every sender's spec (`[[commands]] target`); registration refuses a non-owner, and a sender whose owner is not registered (SPR-006 G5). Every consequence of a death goes through one path: ledger removal, life-course entry, succession trigger, inheritance and the death event. This holds whichever system caused the death (M2, M5, M8 or an agenda action).
3. **Systems never call each other.** They communicate through owned tables, lifecycle commands and events.
4. **The scheduler is derived, not hand-ordered.** Within each phase, system order is a topological sort of the declared read/write sets, with ties broken by system ID. A dependency that runs against phase order must be declared as a **lag**: the reader sees the value from the previous instant. That keeps the visibility rules explicit. The order is defined exactly as follows (SPR-005; `rh_core::schedule`):
   - **Binding.** Within a phase the unit of scheduling is the **binding**, a system at one pulse (system, pulse), not the system (DEF-7, Architect ruling).
   - **Edge.** When system R reads at `same_instant` a column system W writes (W ≠ R), every binding of W in a phase precedes every binding of R in that phase, whatever their pulses. Two bindings of one system have no edge between them. A read declared with a lag (`start_of_day`, `previous_pulse`, `lagged`) creates no edge. A `same_instant` read of a column written in a later phase is a registration error, and so is a cycle of edges within a phase. The graph is built once, at registration, over every binding in the phase: it covers every instant, so the bindings firing at any one instant are acyclic too.
   - **Lags.** A read declares one of four lags (the `[[reads]] lag` of the system specs):
     - `same_instant`: the value written earlier in this instant. It creates an edge, so the owner runs first.
     - `lagged`: the value at the start of the current instant.
     - `start_of_day`: the value at the start of the current day's first instant.
     - `previous_pulse`: the value at the end of the instant in which the reader last fired on this binding; at its first firing, the initial value.

     None of the last three creates an edge. **P0 approximation (Architect ruling, SPR-005):** all three read the start-of-instant value. Exact `start_of_day` and `previous_pulse` (column snapshots) are BCK-002 A-28, due before the first system that declares them runs (P1a: S5, S6 and S7).
   - **Level.** Computed once, over that full graph. A binding with no predecessor in the phase has level 0. Any other binding's level is one more than the highest level among its predecessors: the length of the longest dependency path that ends at it.
   - **Order.** At each instant the firing bindings run level by level, in increasing order. Within a level, ties go coarser pulse first (Year, Season, Month, Day, Hour), then ascending Registry system id, compared byte-wise as strings (`M2.demography` before `S5.daily_life`), not by the numeric RNG `system_id`. The dependency order is the law; pulse coarseness only breaks ties, so two bindings of one system in one phase are ordered by it.
   - **Timers.** Within each phase, the timers due at `(instant, phase)` run first, in a timer pass over the systems that own them (the order above; each system once, at the level of its first binding in the phase, taking its timers in agenda-key order), then the firing bindings. A timer keyed to `(t, phase)` is a scheduled outcome of that phase and fires before any system steps in it (Architect ruling on SPR-006 D1).
   - **Threads.** The bindings of one level may run on any number of threads, except that two bindings of one system run in turn. Their results are committed, and EventIds assigned, in this order whatever the thread count. Each step writes only into its own buffers (new timers, cancellations, lifecycle commands, event drafts); at the end of each level (a level split because one system's second binding appears counts as two) the buffers merge in this order, and only the merge assigns timer `seq` values and `EventId`s (SPR-006 ruling 1). Within one system the merge takes its cancellations, then its timers, then its events, then its commands, so a command can carry the `EventId` of the event that caused it. A step cannot know an `EventId` before the merge, so it names an event it emitted earlier in the same step by a `DraftRef` (an engine API: `rh_events::DraftRef`, returned by `StepCtx::emit`); as a causal edge of a later draft or as a command's cause, the merge replaces it with that event's id (Architect ruling on SPR-006 D2, D3).
   - **Why levels.** The rule is not the lexicographically smallest topological order (Kahn's algorithm taking the smallest ready id). That order can run a whole chain before an independent system, so it is not the order in which the levels run in parallel.
5. **Verb effects** are typed commands, expressed in the Registry effect language (05.5 §2.1). `rh-minds` does not write directly into other systems' tables.
6. All randomness comes from `ctx.rng(purpose, entity, k)`, or from `ctx.stream(purpose, entity)`, the keyed stream an `rh-sample` sampler call takes (SPR-008, Architect ruling). Both have the same key: `stream(p, e)` is positioned at draw 0, and its draw `k` is `rng(p, e, k)`. Because how many draws a sampler consumes depends on its parameters, each sampler call takes its own stream (§6 item 3). Within one step a `(purpose, entity)` pair is handed out as a stream at most once, and never alongside `rng` draws for the same pair, in either order: `StepCtx` refuses both with `SimError::StreamReuse`, naming the system, the purpose and the entity. A system that needs two samples per entity declares two purposes. Any number of `rng` draws may be taken for one pair.
7. Any quantity that crosses a decision threshold is an integer or fixed-point value (§6).
8. Each system declares its events in the Registry, with roles, act classes and default tellability.

**Validating fidelity levels** (relaxed from v1.0, which made it a ratchet; RT-m2):
- Each level is validated against the **stylized facts** on its own.
- Consistency between F(n) and F(n+1) is required only for **conserved quantities** and **declared targets**.
- A published **supported-combinations matrix** lists the fidelity mixes that are tested.

**Coexisting fidelities** (restricted; RT-M6):
- **On-map demography is always per-person (F1+).** Variety comes from cadence and richness, not from switching representation.
- F0 cohort compartments exist **only for off-map (T−1) populations**. A **materialisation adapter** creates immigrants with IDs `H(seed, "immigrant", origin, t, k)` and "unknown parents" provenance.
- Other systems that mix levels across a boundary (e.g. an F0 price index next to F1 goods markets) must declare **boundary adapters**: lift and project operators, with conservation and distribution tests.
- **Fidelity switches happen only through a migration keyframe**, never mid-run in a rollout.

### 3.1 Era-generic rule (ADR-0027)
Worlds must be able to pass from agrarian to modern conditions in one run. So:
1. **No system hard-codes an era.** Every era-sensitive parameter is a Registry function of the **era-state vector** (technology adoption, energy per capita, urban share, literacy, fiscal capacity, executive constraint, succession institutionalisation, franchise, medical and sanitation level). Constants remain only for quantities the sources show to be era-invariant, such as the shape of the war-severity tail.
2. **Mechanics never read the era label.** The label (agrarian, early-modern, industrialising, industrial, contemporary) is computed from the vector for presentation, narrative and validation band selection only.
3. **Modern-capable mechanisms are present from the start** and dormant until the state activates them: an industrial sector at zero share, a fertility response to child survival and literacy that is flat in agrarian conditions, rail-dependent logistics. In-run era change is never a fidelity switch.
4. **Era packs** add coverage over time. Until a pack exists, its technologies are beyond the engine frontier: a world that reaches the frontier keeps running at the last supported era and files a gap report, then continues under the next build through a migration keyframe.
5. **Hazards depend on institutions, not on dates.** The sources reject a global "civilising trend" flag: deposition fell in the medieval West but rose in the Islamic world over the same centuries (Blaydes & Chaney 2013), and regicide fell as succession was institutionalised (Eisner 2011). Trends must emerge from institutional state.

## 4. Time and scheduling

### 4.1 Sim-time and calendar
- `SimTime = i64` minutes from the world epoch. Negative values are allowed, so founders can be born before year 0 (ADR-0026).
- The calendar has **12 months**.
  - `days_per_year` is 360 (30-day months) or 365 (31, 28, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31).
  - Seasons are 2 or 4, in equal runs of whole months starting at month 1: with four, at months 1, 4, 7 and 10; with two, at months 1 and 7 (SPR-005 audit).
  - There are no leap years.
- **Pulses:** `Year`, `Season`, `Month`, `Day`, `Hour`. Inside the bubble there is also a presentation-only `Realtime` pulse.
- **Adaptive daily stepping.** M5, M8 and siege mechanics request `Day` pulses only for *active* regions, armies and sieges. Activity is decided at the preceding coarser pulse.
- **Scheduled outcomes (ADR-0025).** Systems sample the intra-pulse times of state-changing outcomes for everyone and insert them as **timers** in the agenda. Timers fire at their own tick in every mode. No event is ever emitted with a tick earlier than the current instant.

Events emitted in phase *k* are visible to later phases in the same instant only through owned tables. Reverse dependencies require declared lags (§2 rule 4). The sifter (plane C) consumes events in emission order.

### 4.3 Named-actor agenda (RT-M1)
- **Queue.** A binary-heap discrete-event queue holding **decisions and timers**, keyed by `(time, phase, entity_id, seq)` (SPR-006 ruling 2):
  - `entity_id` is a typed key with a total order: the entity-kind tag first, then the id's integer value (`rh_ids::EntityRef`);
  - `seq` is a `u64` from one counter per timeline, assigned at the merge (§2 rule 4) and never reused, so keys are unique and the pop order is a pure function of them;
  - cancellation is by `TimerId` with lazy deletion (a tombstone checked at pop); a cancelled timer never fires;
  - the state a keyframe stores is a sorted dump of `(key, timer)` pairs, the counter and the tombstones (ruling 7);
  - **firing order** (Architect ruling on SPR-006 G1): at one `(t, phase)`, an owner's timers fire in key order, and owners fire in the canonical binding order of §2 rule 4, because each owner's timers run at the level of its first binding in the phase (the timer pass, D1);
  - **one slot fires together** (Architect ruling on SPR-006 G2): the timers due at the same `(t, phase)` leave the agenda together, before any of them fires, and fire simultaneously against the same state, so one firing cannot cancel a sibling in its slot; a cancellation takes effect from the next `(t, phase)` slot. This is the "simultaneous deliberation, ordered action" principle below. Conflicts such as "dead and acted" are settled when the lifecycle queue is applied: a command for a person who died earlier in that application is dropped with a diagnostic (BCK-002 A-30, due with the first death command, M2, P1a).
- **Polling.** Per-decision-type polling intervals in the CK3 style (1–12 months).
- **Interrupts.** An event perceived above an actor's salience threshold schedules a re-evaluation at the **next instant at the earliest** (t + 1 day by default), with a per-actor daily cap. Ping-pong loops within one instant are impossible.
- **Same-instant semantics: simultaneous deliberation, ordered action.**
  1. The snapshot is taken at the **start of the `Agenda` phase**, after phases 1–8.
  2. Every due decision is *scored* in parallel against that snapshot. Response curves are **fixed-point lookup tables**, so threshold comparisons are platform-independent.
  3. Each chosen action declares its **preconditions** and its **read and write key sets** (e.g. `office:5`, `person:H…`, `market:12:grain`).
  4. Actions are applied in a **keyed permutation order** `H(seed, salt, t, entity_id)`. This avoids the founder and low-ID bias of `entity_id` order.
  5. An action is **invalidated** when an earlier applied write set intersects its read set *and* its precondition now fails.
  6. An invalidated actor re-scores **once** against the updated state. If its new choice is also invalid, it defers deterministically to the next poll.
  7. Worst-case serial work is one re-score per actor per instant. This is budgeted in `08` §1.
- **In the bubble**, embodied actors' moment-to-moment behaviour is a **view** (plane B), not authoritative re-evaluation.

### 4.4 Time controls
- Speed bands, in sim-time per wall-second: Live · 1 h/s · 1 d/s · 1 wk/s · 1 mo/s · 1 yr/s · 1 decade/s · **MAX**.
- T3/T4 hydration exists only at **Live**, where the street clock runs at 20–60:1. Faster bands collapse the bubble.
- **Run-until** stops on a date, a predicate over aggregates, or `next_match(salience ≥ θ)`.
- Speed bands change only the publish cadence and how far `advance_until` goes per wall interval. **They never change the simulation for a given input journal.** No step waits on a model (ADR-0034), so MAX speed runs the same history as any other band.

## 6. Determinism contract (ADR-0006, amended by ADR-0024/0025/0026)

1. **History function.** `history = f(engine_build, registry_version, manifest_hash, seed, input_journal)`. It covers plane A. Planes B and C are pure functions of A plus their own versions and inputs.
2. **Keyed RNG.** Every draw is `u = H(world_seed, branch_salt(t), system_id, epoch, purpose, entity_id, t, k)`. `H` is ChaCha8 with stream and position (decided in SPR-002; the exact layout follows); SplitMix64 serves scalar hashes. `epoch` is 0 unless a material input has re-sampled the entity (ADR-0025).
   - **Byte layout of `H`, version 2 (normative; implemented by `crates/rh-ids`).** The key also carries the entity's `epoch`, the count of material inputs that have re-sampled it (ADR-0025 item 3). `H` is ChaCha8: the original Bernstein ChaCha with 8 rounds, a 64-bit block counter in state words 12–13 and a 64-bit nonce in words 14–15. All integers are **little-endian**; `t` enters as its two's-complement `u64`. `PRF(K, nonce, block)` is the first 32 bytes of ChaCha8 block `block` with nonce `nonce` under key `K`. Then `K1 = PRF(K0, branch_salt, system_id | epoch << 32)`, `K2 = PRF(K1, purpose, entity_id)`, and the stream of a key is ChaCha8 under `K2` with nonce `t`.

     | # | Field | Width | Where it enters |
     |---|---|---|---|
     | 1 | `world_seed` | `u64` | `K0` bytes 0–7; bytes 8–31 are the domain tag `"rehoboam/rh-ids/H/v2"` and 4 zero bytes |
     | 2 | `branch_salt(t)` | `u64` | `K1` nonce |
     | 3 | `system_id` | `u32` | `K1` block counter, bits 0–31; the high 32 bits of `h64_bytes(tag("rehoboam/rh-core/system/v1"), id)` for the Registry system id `id` (SPR-005); a collision is a registration error, and renaming a system is therefore a C3 change |
     | 4 | `epoch` | `u32` | `K1` block counter, bits 32–63; 0 unless a material input has re-sampled the entity |
     | 5 | `purpose` | `u64` | `K2` nonce; the identifier hashed from the purpose name |
     | 6 | `entity_id` | `u64` | `K2` block counter |
     | 7 | `t` | `i64` | stream nonce |
     | 8 | `k` | `u64` | stream position: `u` is stream words `2k` (low half) and `2k + 1` (high half) |

     `epoch` and `k` enter different steps, so a draw index can never stand in for an epoch. Version 1 had no `epoch`. The scalar hash (SplitMix64), light-stream, salt and `PersonId` layouts are documented in `crates/rh-ids`. All of them are pinned by golden vectors that `bin/gen_rng_golden.py` generates from an independent reference implementation. Changing any byte of a layout is a C3 change.
3. **Vendored samplers.** Binomial (BTPE plus inversion), Poisson (PTRS), normal (ziggurat with fixed tables), Beta, Gamma. Each has golden vectors (V-DET-09). They live in `crates/rh-sample`, **the only plane-A crate where float arithmetic is allowed** (SPR-003 Architect ruling, 2026-10-16):
   - `bin/lint_arch.py` pins the crate to (A, machinery) by name; it is an allowed dependency of `rh-sys-*`. `bin/lint_forbidden.py` exempts it, by that name, from the float rule only; every other V-DET-19 rule applies, and positive controls show the exemption reaches no other crate.
   - Transcendentals come from `libm` only (pinned exactly, default features off). `clippy.toml` disallows the `std` float transcendentals workspace-wide; `sqrt` is allowed (correctly rounded by IEEE 754); `mul_add` stays forbidden. `libm::fma` is allowed: it is a correctly rounded software FMA and gives the same bits on every target. The ban is on hardware contraction and `mul_add`, whose results depend on the target (VER-SPR-003 GAP-5a).
   - Floats never leave the crate: the API returns counts or `rh_core::fixed` values, converted from the exact `f64` value, rounded half to even, with no `as` cast.
   - Draws come from `rh-ids`'s keyed streams, read sequentially; each sampler documents how many draws it consumes.
   - **Call-site rule.** How many draws a sampler consumes depends on its parameters: a degenerate parameter (`p = 0`, `n = 0`, `λ = 0`) draws nothing, and rejection loops vary. So **each sampler call takes its own keyed stream**, never several samples from one stream across which counterfactual parameters can differ; otherwise a parameter change in one branch shifts every later sample and breaks common random numbers (item 9; VER-SPR-003 GAP-7).
   - The algorithms are ported from `rand_distr` (MIT OR Apache-2.0, with its licence header); Poisson's PTRS is written from Hörmann (1993), because `rand_distr`'s Poisson is not PTRS.
4. **Numerics.**
   - Counts, money (i64 minor units), psychology (Q8.8 / Q16.16), timers and IAUS curves are integer or fixed-point.
   - Floats are used only in fields and continuous dynamics, evaluated in fixed order with `libm`. No `mul_add` and no fast-math; C dependencies are built with `-ffp-contract=off`: the repository's `.cargo/config.toml` sets `CFLAGS` to exactly that for the `cc` builds (bundled SQLite, zstd), and `bin/check_all.sh` checks the build-script output records it (SPR-007 ruling 4). rustc never contracts `a * b + c` into an FMA by default; `bin/check_all.sh` fails if any `RUSTFLAGS` variable mentions `fp-contract`, or if a `CFLAGS` variable or a `.cargo/config` in the repository holds any `fp-contract` other than `CFLAGS = -ffp-contract=off` (VER-SPR-003-TEST GAP-6; SPR-007 ruling 4).
5. **Iteration and parallelism.**
   - No hash-map iteration in authoritative paths.
   - Rayon only with fixed chunking (65,536 elements), and chunk-ordered reductions.
   - Authoritative ECS queries are sorted by `PersonId`.
6. **Hashes.** `state_hash` (plane A), `observation_hash` (B) and `narrative_hash` (C) are separate. Each is a chunked Merkle xxh3 with dirty tracking, taken monthly in CI and debug builds and yearly (configurable) in release builds. Per-table Merkle roots enable a **divergence bisect tool**, which reports the first divergent month, table and row.
   - **Byte layout of the plane hashes, version 1 (normative; implemented by `crates/rh-snapshot/src/hash.rs`).** `XXH3(b)` is XXH3-64 with seed 0 and the default secret (`twox-hash`). Integers are little-endian; `u8`, `u32`, `u64` are their 1, 4 and 8 bytes; `‖` concatenates. Each level hashes under its own domain tag, the ASCII bytes, without terminator, of `D_CHUNK = "rehoboam/rh-snapshot/hash/v1/chunk"`, `D_TABLE = "rehoboam/rh-snapshot/hash/v1/table"` and `D_PLANE = "rehoboam/rh-snapshot/hash/v1/plane"`. A table defines each row's canonical byte encoding `row(i)` and the key order (the P0 stub column: its `i`-th `i64`, 8 two's-complement bytes, in index order). Chunk `c` holds rows `[1024c, min(1024(c+1), n))` of a table with `n` rows, and `chunk(c) = XXH3(D_CHUNK ‖ u64 c ‖ u64 m ‖ (u32 len(row) ‖ row)…)` over its `m` rows in order; a table has `⌈n/1024⌉` chunks. The table root is `XXH3(D_TABLE ‖ u32 len(name) ‖ name ‖ u64 n ‖ u64 k ‖ u64 chunk(0) ‖ … ‖ u64 chunk(k−1))`, with `name` the table's UTF-8 name and `k` its chunk count. The plane hash is `XXH3(D_PLANE ‖ u8 p ‖ u64 t ‖ (u32 len(name) ‖ name ‖ u64 root)…)` over the plane's `t` tables in strictly increasing byte order of their names, with `p` the ASCII letter `A`, `B` or `C`; so two planes with identical tables never hash equal, and planes B and C hash `D_PLANE ‖ u8 p ‖ u64 0` until they gain tables. **Version line:** the version is the `v1` component of every tag. Any change to these bytes is a new version with new tags (`…/hash/v2/…`) and regenerated golden vectors, and a C3 change. `bin/gen_hash_golden.py` re-implements XXH3 and this layout in the Python standard library and generates the golden vectors that `crates/rh-snapshot/tests/golden.rs` reproduces.
   - **What `state_hash` covers (SPR-007 T-02).** `state_hash` covers authoritative plane-A state only. That is the world columns *and* the engine-held state: pending timers, lifecycle command queues, scope epochs, queued material inputs, the engine counters, and the event log's next EventId and running event-log hash. `rh_snapshot::state_hash` hashes `Engine::snapshot()` (an `EngineState`) as one plane-A hash over the world columns (named `entity.column`) and seven engine tables (`rh-core/agenda.meta`, `rh-core/agenda.timers`, `rh-core/engine.commands`, `rh-core/engine.epochs`, `rh-core/engine.inputs`, `rh-core/engine.meta`, `rh-core/events.meta`). Their normative row encodings are documented in `crates/rh-snapshot/src/state.rs` and re-implemented in `bin/gen_hash_golden.py`. The undrained events, `rh-core/events.held`, are a **carried table**: a keyframe stores them, so a load restores the pending channel-A output, but `state_hash` does not read them. Draining is the host's act and is in neither the journal nor the history tuple, so hashing held events would let watching change history. History is already committed by `rh-core/events.meta`, whose running hash draining does not reset (SPR-006 G4), so `state_hash` is drain-independent. (Architect ruling on VER-SPR-007-TEST round 2 GAP-6, which replaces the T-02 plan ruling that put held events in the hash.) `rh_snapshot::tables_hash` hashes the world columns alone. Two engines whose world columns agree but whose pending timers differ hash differently, so a keyframe that lost a timer is refused. Two runs that emitted different events and then converged also hash differently, through the running hash.
   - **Keyframes (SPR-007 T-02; V-DET-05).** A keyframe is format `rehoboam/rh-snapshot/keyframe/v1` (`crates/rh-snapshot/src/keyframe.rs`): an envelope (8-byte magic, XXH3-128 of the rest) around one Arrow IPC file, zstd level 3, with two columns `table: Utf8, row: Binary` that hold every table of the `EngineState` in the canonical row encoding the hash reads, and a header table carrying the history tuple, the journal position and `state_hash`. A load checks the envelope, the header's row counts, the history tuple and the stored hash, restores the engine in canonical form only (`Engine::restore`) and hashes it once more. `rh_snapshot::store::KeyframeStore` keeps every 10th sim-year for good and the other years in an LRU (default capacity 8); the host places the files.
   - **Keyframe loading is hardened (VER-SPR-007-TEST round 2 DEF-3; ADR-0007 keeps Arrow IPC with zstd).** Arrow 60 trusts an IPC body's declared sizes: a forged uncompressed length makes it allocate before decoding, and a failed allocation aborts the process. A body with a correct envelope digest can still be wrong (a buggy writer, another Arrow version), so loading has four layers:
     1. `rh_snapshot::ipc_guard::check` validates the IPC metadata with `arrow-ipc`'s verified flatbuffer accessors before `FileReader` sees the bytes. It checks the schema, the block and buffer offsets, the row counts and every declared uncompressed length. A values buffer may declare at most 64 MiB (`MAX_VALUES_BYTES`), an offsets buffer `4 (rows + 1)`, a validity buffer `rows / 8 + 64`, and never more than 32,768 times its compressed bytes, which is zstd's own expansion limit. One batch can therefore make Arrow allocate at most about 129 MiB. The writer splits batches to stay within these bounds.
     2. `catch_unwind` around the guard and the decode maps a panic to `KeyframeError::Panicked`, so the no-panic claim does not rest on the guard being bug-free (DEF-3b: the guard once panicked on a negative `bodyLength`). Allocation aborts cannot be caught; layer 1 prevents them.
     3. `write_keyframe` reads every keyframe back and refuses (`KeyframeError::ReadBack`) one that does not decode to exactly the state and header it was written from.
     4. A regression sweep flips single bits across the Arrow body, re-seals the envelope and requires zero panics, zero aborts and no other state accepted. The PR tier takes every bit of every 29th byte; the nightly tier takes every bit of every byte (about 94,000 loads). A structured forge test covers what single bit flips cannot reach. It sets every footer block's `offset`, `metaDataLength` and `bodyLength`, and, in the first message, every buffer `offset` and `length`, every node `length` and `null_count`, and the batch `length`, to 0, -1, -8, -16, -256, the extremes, the true value ± 8 and the file length. Each forgery must be refused or load the equal state.
   - **Keyframe history and journal anchor (VER-SPR-007-TEST DEF-4, GAP-7).**
     - **History tuple:** `write_keyframe(engine, journal)` takes it from the engine (`Engine::provenance`, `Engine::world_seed`, `Engine::branch_salt`), never from its caller. A keyframe cannot be stamped with another seed or salt, which `state_hash` does not cover.
     - **Count (VER-SPR-007-TEST GAP-10):** the journal position is the number of inputs the engine has *accepted*, applied or still queued (`Engine::journal_position`, stored as `accepted_inputs` in the hashed `rh-core/engine.meta`); the applied count is that less the queued inputs. The header's `JournalPosition` must be the engine's timeline and equal that count. Both write and load check it, so an edited count is refused even without the journal. A keyframe at position `p` holds exactly the effects of the journal's first `p` rows in `seq` order: applied ones in its tables, queued ones in its `inputs` table. Resuming re-submits only the rows from `seq p` on. The applied count would be the wrong position: inputs apply in tick order, not `seq` order, and the queued ones would apply twice. A crash artifact's `journal_position` is the same count, and `Engine::replay` requires the host to have submitted exactly that many journal rows first.
     - **Host order:** check the input against the engine's cursor, journal it, then submit it. Journal order is then acceptance order, and a journaled input is never refused.
     - **One row, one input:** a journal row's scope is one entity, and a journaled run submits exactly `rh_snapshot::resume::material_input(row)` for each row. The engine's set-valued `MaterialInput` scope is wider than the journal; an input submitted outside the journal makes the run unresumable (Architect, SPR-007 audit).
     - **Chain:** `Replay::check_anchor(&JournalPosition)` checks the anchor against the journal: at least that many inputs, and the chain after them equal to the head. Call it wherever a keyframe is loaded together with a journal. It catches a tail truncated with a forged count and head, and a journal re-grown with other inputs.
     - **`rh_snapshot::resume::resume`** is the host loop: load the keyframe, `check_anchor`, then submit the journal's rows after the position in `seq` order. SPR-008's bisect reuses it.
     - **Non-material inputs (BCK-002 A-33):** when they reach the engine, they are counted the same way, as accepted journaled inputs.
7. **Plane isolation.**
   - A lint forbids plane-A crates from depending on B or C crates.
   - Read-only consumers get immutable frames. A runtime unsynced-guard hash check runs only in debug and CI.
8. **Journal integrity.**
   - **Push inputs** (player actions, speech acts, Oracle verbs, settings) apply at their tick. They are the only input class: pull inputs are retired (ADR-0034).
   - Replay **hard-fails** on a missing, extra or mismatched input. There is no silent fallback.
9. **Branch salts and common random numbers** (RT-M4).
   - `branch_salt(t) = H(the lineage path of forks covering t)`. The canonical timeline's path is empty; every Foresight job and rollout extends it uniquely, so salts never collide.
   - **Pre-sampled futures.** Timers and polls drawn before a fork are re-drawn after the fork only if their purpose is flagged `resample_on_fork` in the Registry (vital timers, latent periods). Otherwise they are shared.
   - **What-if forks** keep the parent salt by default, giving a clean counterfactual. A "reroll fate" option extends the salt.
   - **Common random numbers survive across branches** because person IDs are genealogical (ADR-0026). Paired intervention rollouts share draws for every unaffected lineage.
10. **Golden runs.**
    - On every PR: `smoke` runs 1,000 years and the other reference worlds run 200 years. All reference worlds run the full length nightly. Hashes are compared every sim-year. The schedule matches `13` §4.
    - Guarantee level 1: bit-exact on the same binary, OS family and architecture.
    - Level 2 (goal): bit-exact across platforms.
11. **Change classes** (agent governance, `13` §4).
    - A *refactor* must be hash-neutral.
    - A *model change* is auto-approved if the 32-seed CRN-paired stylized-fact ensemble stays within tolerance.
    - Only out-of-tolerance changes go to you.

## 7. Lifetime, genealogy and great houses

- **Every person ever born** is recorded in the life-course log (plane A), so genealogy is complete for everyone.
- **The live ledger holds only the living.** Dead rows leave at once through the lifecycle queue, and a death-count aggregate is updated per (region, decade, cause, class, age band), plus annual deaths per (settlement, year, cause) for the mortality-crisis detector (`09` V-SF-03).
- **Great-house dormancy (SIM-9).** Great houses grow roughly 2.5× per generation. Members more than N degrees from any title, claim or office become **dormant**: they stay in the ledger and life-course log as ordinary persons rather than T1. They are re-promoted by simulation criteria, such as a claim activating or an office being granted.

## 8. Drama couplings to implement first (R09)

1. **Famine → unrest → succession crisis.**
   - Two bad harvests (M3) send grain prices up, typically ×1.5–2 and ×3–4 in the worst famines (M4; ×3–5 is the extreme tail, R12 §17).
   - Entitlement collapses and deaths rise (M2); marriages are postponed and births fall. The age pattern of famine deaths is not yet sourced.
   - Mass mobilisation potential and fiscal stress rise (M6), raising the regicide hazard (M7).
   - With ~0.3 probability the heir is a child, which brings a regency and then civil war.
   - Armies eat the remaining grain (M8, so the full chain completes in P3; the G1b test truncates at regency or civil-war onset).
2. **Plague → paranoia → purge → labour revolt.**
   - An outbreak (M5) raises fear, which produces multiple epidemic waves.
   - Scapegoats come from the out-group (S1.culture), and purges cut legitimacy.
   - Wages rise while rents fall, which squeezes elites and leads to wage freezes.
   - A Granovetter cascade ends in revolt.
3. **Hive detection spiral (modern).**
   - At low prevalence most positive tests are false, so innocents are detained and legitimacy and paranoia move against the state.
   - People avoid testing and falsify preferences, so covert spread accelerates.
   - As prevalence rises, PPV improves, and "the purges were right" becomes the political narrative.
4. **Elite overproduction.** Prosperity leads to elite growth, then feuds, then a 40–60-year violence wave.
5. **Dragon raids.**
   - A livestock boom raises raid frequency (individual dragons' hunting hazards rise with available prey), leaving famine pockets.
   - Hunting dragons brings prestige.
   - Dragon *numbers* change only through individual life-history hazards within the energetics bound. There is no "boom" beyond what prey biomass supports.

Each coupling is tested as a **scenario test**: the chain must be *possible* (it completes in ≥ x% of an ensemble) and *not forced* (it is absent in ≥ y%). x and y are set numerically before each phase starts (`11`).

## 9. Invariants (minimum set)

- **Population conservation.** Births − deaths ± migration equals the change in the living ledger, per region per month. This is reconciled with life-course log entries.
- **Conserved compartments.** Food, coin and pathogen counts are conserved apart from declared sources and sinks.
- **No negatives.** No negative compartments, stocks or counts.
- **Genealogy.** It is acyclic. A child's birth is at least the minimum parental age after each parent's birth.
- **Life-course consistency.** Every living named actor has a living ledger row. Every ledger row has an open life-course entry.
- **Exclusive relations.** One ruler per title, one location per person.
- **Valid IDs.** No ID collision is left unresolved, and every `PersonId` matches its derivation rule.
- **Plane isolation.** No plane-A table contains plane-B or plane-C references.

## 10. Python prototyping lane

New models may be prototyped first in Python (NumPy/Numba, marimo), against the same Registry parameters and a fixture world exported through `rh-py`.
- **Promotion to Rust.** A model is promoted once it passes the stylized-fact bands.
- **Port verification.** The Rust port must match the prototype's declared aggregates under a **statistical equivalence test (TOST)**, not a bitwise one.
