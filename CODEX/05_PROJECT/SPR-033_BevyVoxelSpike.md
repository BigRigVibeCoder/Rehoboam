## The level-of-detail fallback (D62)

**Levels.** L0 is the canonical content at 0.35 m. L1 (0.70 m) and L2 (1.40 m) are exact 2×2×2 reductions of the level below. The rule: a coarse voxel is solid when at least 4 of its 8 children are solid, and it takes the most frequent material among them, ties to the lowest id. The reduction is integer and a pure function, so every level is reproducible. The red team's 0.65 m and 1.0 m tiers are not power-of-two multiples of 0.35 m and would need resampling, so they are not used (F3).

**Rings and notches.** Around the camera's ground point:

| Notch | L0 (0.35 m) within | L1 (0.70 m) within | L2 (1.40 m) within | Beyond |
|---|---|---|---|---|
| 0 (default) | 90 m | 360 m | — | heightfield mesh from the cell raster (30 m) |
| 1 | 45 m | 360 m | — | heightfield |
| 2 | — | 360 m | — | heightfield |
| 3 | — | 180 m | 360 m | heightfield |
| 4 | — | — | 360 m | heightfield |

**How the notch is chosen (`--lod auto`, the default).**
1. **Calibration at start.** The viewer flies a fixed 10-second orbit at 60 m around the focus seat at notch 0, after the bubble has loaded, and records every frame time. If the 95th percentile is at most 16.7 ms it keeps notch 0. Otherwise it moves down one notch and measures again for 5 seconds, until the percentile fits or notch 4 is reached.
2. **Adaptation while viewing.** The viewer keeps a window of the last 120 frames. If the window's p95 exceeds 16.7 ms three windows running, it moves down one notch. If p95 stays under 11.7 ms (70% of the budget) for ten windows running, it moves up one. The hysteresis keeps it from oscillating.
3. **`--lod fixed:<notch>`** disables both, for measurement.

**How it is reported.** Every change prints one line on stdout and in the HUD, for example `lod 12.4s p95=18.2ms notch 0->1 (p95 > 16.7 ms over 3 windows)`. At exit a summary line gives the time spent at each notch and the final notch. The FPS report (below) carries both.

**What it never changes.** Voxel content. V-R3D-13's digest is always over L0 content of the fixed bubble, whatever is drawn, and the level a chunk is drawn at is rendering, not hashed.

#### T-02: Chunks, the mesher, the level reduction and the digests (`rh-view-core`; 0.6 day)
- **Deliverable:**
  - **`chunk.rs`:**
    - 62³ chunks, stored padded to 64³ as `u16` material ids, in the crate's ZXY order;
    - chunk coordinates per level;
    - padding filled from the neighbours, so a face on a chunk boundary is culled exactly when its neighbour is solid;
    - `palette_v0`: air, water, sand, grass, dirt, rock, packed earth, stone, plus reserved ids for SPR-034's building materials.
  - **`mesh.rs`:**
    - a thin adapter over `binary_greedy_meshing::Mesher::<62>::fast_mesh` with the opaque mask; water is transparent;
    - packs each quad's corners into 32-bit vertices: 6 + 6 + 6 bits of position, 3 bits of face and 11 bits of material;
    - meshes chunks on N threads and returns results ordered by chunk coordinate, never by completion.
  - **`lod.rs`:** the 2×2×2 reduction of the fallback section.
  - **`digest.rs`:**
    - **the content digest:** XXH3-128 over the generator versions, the bubble's definition (focus settlement, centre, radius) and each L0 chunk's coordinates and padded-out interior in coordinate order;
    - **the mesh digest:** XXH3-128 over each chunk's quads and vertex buffer, bound to the mesher crate's version and the packing version (PRJ-003 §5's second check).
- **Acceptance:**
  - **Face culling:** unit tests on a solid cube, a hollow box, a single voxel, a one-voxel tunnel, and faces on each of the six chunk boundaries with solid and empty neighbours.
  - **The differential test (the oracle is our own):**
    - A naive mesher emits one 1×1 quad per visible face. Over 1,000 fixed-seed SplitMix64 chunks (density 0–100%, 1–16 materials), the greedy quads cover exactly the oracle's faces: each face once, with its material and direction, no overlap and no gap.
    - A planted `mutant-mesh-drop-face` feature, which drops the last quad of one direction, must FAIL this test by name.
  - **Determinism:** quads, vertices and both digests are equal across two runs and across 1 and 4 meshing threads.
  - **Level reduction:** exact on all-solid and all-empty chunks; unit tests for the majority and tie rules; L1 and L2 digests equal across runs.
  - **Reported, not gated:** the median and p95 time to mesh one chunk on one core, over 200 terrain chunks (an `#[ignore]` timing test, run by `check_viewer.sh` with its figures in the report). The red team's bound was 3.0 ms; the crate's own figures are 65–300 µs.

#### T-03: `hamlet`'s real terrain from worldgen-lite's exact reference (0.6 day)
- **Deliverable:**
  - **`viewer/tools/export_worldgen_lite.py`** (run with the repository's `python/.venv` interpreter and `-I`):
    - **`--world <name>`** reads `worlds/<name>/world.toml`, checks the manifest's SHA-256 against its pin (the engine's own rule, SPR-011 ruling 16), and reads the manifest through `specs/manifest/manifest_v0.py`'s loader: geography, seed, cast, households and the rest. **`--manifest <path>`** does the same for a manifest with no `world.toml` yet (`twin_vales`).
    - It loads `specs/worldgen/selftest_worldgen_lite.py` by path, as `selftest_fixture_worlds.py` does, runs `generate` and, when the manifest gives the whole population, `placement`.
    - It writes the export format of the specs table into `--out`.
    - **`--check`:** recomputes, and when the case is in `worldgen_lite_v0.txt`, compares every golden line of the case (`elevation_sha256`, `land`, `seeds`, `regions_sha256`, `land_cells`, `seats`, `edges`, `routes`, `graph`, `residence`).     - **`--control shifted-seed`:** the same check with the seed plus one; it must FAIL with `STALE`.
    - Standard library plus the project's own modules; `ruff` and `mypy` clean under the root's configuration.
  - **`rh-view-core::export`:** reads the format and refuses a file whose raster length or header disagrees, by name.
  - **`rh-view-core::terrain` (`terrain_v0`):**
    - **The scale:** 30 m per cell horizontally, 1/64 m per elevation unit (the specs table).
    - **Interpolation:** each 0.35 m column's elevation is a bilinear interpolation of the four nearest cell centres, in `i64` with one stated rounding rule; its height in voxels is `floor(e × 100 / 2,240)` (64 units per metre, 0.35 m per voxel).
    - **Materials:** below the template's sea level the column is seabed under water up to sea level; land within 2 m of sea level is sand; a column more than 3 voxels above a neighbour is rock; otherwise grass over 3 voxels of dirt.
    - **Shell only:** each column is filled 6 voxels below its surface and empty beneath, so chunks stay sparse.
    - **Seats:** a 12 m square stone plaza, levelled at the seat's surface height.
    - **Routes:** one straight packed-earth strip, 4 voxels wide, between the seats of every region edge in the export, draped on the surface. It replaces the surface material and never changes height.
    - **Chunks** are generated on demand from these pure functions and dropped after meshing; only meshes are kept.
  - **`viewer/golden/terrain_v0.txt`:** the content digest of `hamlet`'s settlement-1 bubble at L0 (90 m) with `terrain_v0`'s version, and the L1 digest. It is written only by `cargo run -p rh-view-core --bin terrain_golden -- --write`.

## How the director runs it (as planned)

Paths are examples. A run directory must be new; socket paths stay under 107 bytes (`wire_v1.md` §1). The pace flag needs SPR-027; until it merges, omit `--pace 1y`, and `hamlet` runs 200 years in about a second at `max`, so the HUD shows the tip racing to `stream.end`.

**Once per checkout, on the laptop:**
```bash
cd ~/Rehoboam
uv sync --frozen --project python
python/.venv/bin/python -I viewer/tools/export_worldgen_lite.py --world hamlet --out target/viewer/exports --check
(cd viewer && cargo build --release -p rh-view)     # first build about 10-15 minutes on the P51
```

**A run on the laptop, with the viewer beside it:**
```bash
# terminal 1: the engine, serving A.sock
cargo build --release -p rh-cli
install -d -m 0700 ~/rh-runs
target/release/rh-cli run hamlet --years 1000 --run-dir ~/rh-runs/hamlet-1 --socket --pace 1y

# terminal 2: the viewer
target/viewer/release/rh-view --world hamlet --run-dir ~/rh-runs/hamlet-1
```

**A run on `adjutant`, viewed on the laptop through an SSH tunnel to the Unix socket:**
```bash
# 0. Start the VM (RUN-002 §1). `adjutant` is the director's SSH host alias (Tailscale);
#    REMOTE_HOME is the run user's home on the VM, e.g. /home/director.
gcloud compute instances start adjutant --zone=us-central1-a --project=<project>
ssh adjutant 'cd ~/Rehoboam && git pull --ff-only && cargo build --release -p rh-cli && install -d -m 0700 ~/rh-runs'

# 1. One terminal holds the run in the foreground of an interactive session and carries the
#    tunnel. The interactive session is what keeps the VM awake: its idle shutdown counts `who`
#    logins only, so a `ssh -N` tunnel or a nohup'd run would not (F9).
install -d -m 0700 "$XDG_RUNTIME_DIR/rh"
ssh -t -o ExitOnForwardFailure=yes -o StreamLocalBindUnlink=yes \
    -L "$XDG_RUNTIME_DIR/rh/hamlet-A.sock:$REMOTE_HOME/rh-runs/hamlet-1/stream/t0000000000/A.sock" \
    adjutant 'cd ~/Rehoboam && target/release/rh-cli run hamlet --years 1000 --run-dir ~/rh-runs/hamlet-1 --socket --pace 1y'

# 2. Another terminal: the viewer, on the forwarded socket (it retries until the run has made A.sock)
target/viewer/release/rh-view --world hamlet --socket "$XDG_RUNTIME_DIR/rh/hamlet-A.sock"

# 3. When done: Ctrl-C in terminal 1 ends the run and the tunnel, and logging out lets the VM's
#    30-minute idle shutdown run (RUN-002 §3 item 3).
```
Over IAP instead of Tailscale, replace `ssh … adjutant '…'` with `gcloud compute ssh adjutant --zone=us-central1-a --project=<project> --tunnel-through-iap -- -t -o ExitOnForwardFailure=yes -o StreamLocalBindUnlink=yes -L … '…'`.
