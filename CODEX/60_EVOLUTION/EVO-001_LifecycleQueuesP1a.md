> **BLUF:** `05.1` §2 rule 2 said a command's owner "receives its queue when it next runs" and stopped there. SPR-014 cannot be planned on that sentence: it does not say whether a command sent at `Polity` reaches an owner stepping at `Agenda` of the same instant (it does, in the code and in M7's and T1's specs), which of an owner's bindings takes it, what happens to a command for someone who died in the same slot (BCK-002 A-30), how old a queued command may get (A-31), what registration does with a read or a send whose owner no P1a world registers (REV-P1a NEW-4), or how the merge treats an `EventId` carried in a payload field (REV-SPR-017 N3). This EVO, in its third round after the independent reviews in `REV-EVO-001`, settles the six points as one amendment of rule 2, **applied to `05.1` in PR #49** (the Architect's R8 (f): merging is acceptance; the version number is set at merge, R14), with one sentence each in rule 4, §4.3 and §9. The one choice that was open, whether a dated command may stand in for a timer, is **ruled (R9): shape (b), strengthened**: a command that carries a sampled outcome is submitted only by its sender's own timer, in the outcome's instant, so DET-13, V-DET-12 and ADR-0025 stand as written and nothing goes to the director. ## 1. Problem

**What the contract said.** Rule 2 (`05.1` v1.6): commands are typed, queued by `rh-core`, keyed `(tick, phase, PersonId, seq)`, applied by their one owner, "the owner receives its queue when it next runs"; registration refuses a non-owner and a sender whose owner is not registered (SPR-006 G5). Rule 4 says the merge at the end of each level assigns `seq` and `EventId`s, and that a command's `cause` may be a `DraftRef` the merge replaces.

**What the code does** (`crates/rh-core/src/command.rs`, `engine.rs`). Every job (a timer pass or a binding) is handed the owner's whole queue when it starts (`run_level` takes it; `StepCtx::take_commands`); what the job does not take goes back (`restore`). A step's submissions reach the queues at the merge of the step's level, each with the submitting `(tick, phase)` and the next `seq`; so a command submitted at level L is in its owner's inbox from the owner's next job after L, at any later level, phase or instant. `Command::cause` is the one event-typed slot the merge rewrites; the payload is `Vec<i64>`. Registration reports a read of an unregistered owner and **refuses** a send to one (`register.rs`, rule `command`). Nothing drops a command for a dead person, and nothing bounds a queue's age (VER-SPR-006-TEST GAP-7: 101 commands in 100 days, never applied). The smoke world does send commands (REV-EVO-001 BLK-1): `Settle` from X3 (keyed by the person who just died), X5 and X7, and `Audit` from X4; X4 and X7 take them in one named binding each (`Day`/`Activity`).

**What P1a needs** (PRJ-002 §2, SPR-014's row; §6):

## 2. The amendment (applied: `05.1` v1.10, this PR)

The text is in `05.1` §2 rule 2 (six parts), rule 4's **Threads** bullet, §4.3's **one slot fires together** bullet and §9. In short:

1. **Key and delivery.** A command reaches a queue only at the merge of its level, keyed `(tick, phase, PersonId, seq)` by its submission; from the first run of its owner's draining binding after that merge it is in that binding's inbox, in key order. Delivery within an instant to a later phase is stated (M7 `Polity` → T1 `Agenda`); nothing merged at a level is visible to that level, so the thread count never reaches delivery; the hop count within an instant is bounded by the instant's job count (NIT-3).
2. **Draining.** One binding per command kind, named by the owner's spec (`drained_by`), takes its whole inbox at the start of its step and settles every command; no other job sees the inbox (a timer pass drains nothing: R2). A command carries no date; a command that carries a sampled outcome (`outcome = true` on the owner's `[[applies]]`) is submitted only by its sender's own timer, in the outcome's instant, in the timer pass that precedes every binding, under a purpose the sender re-samples it by (R9, R10, §4). A timer carries one `EventRef` (`cause`) that the merge rewrites, so T1's death timer keeps its `MURDER_ATTEMPT`.
3. **The dead-person drop (A-30).** Only in a world with a ledger, only for `key = "living"` commands, keyed by the `PersonId` field `key_field` names (R13); `rh-core` reads `person.alive` as the level starts (the compaction pass's own exemption); the owner drops its own finds with `StepCtx::drop_command`, a timer firing for the dead with `StepCtx::drop_timer`; one diagnostic for all of it, `dropped{system, kind, reason}` (R11); M2's `apply_death` is idempotent (R1, R3, MIN-5).
4. **Queue age (A-31).** `t − tick < period(pulse(drained_by))` at every `Bookkeeping`: the core invariant `queue-no-stale-command` (R2).
5. **Absent owners (NEW-4).** An identity read always requires its owner: a world without it is refused by name (`absent-owner`), so a P1a spec declares no identity read of a P1b system (R12). A rate or mode read carries a `neutral` (typed, stated by the coupling's prose) and is dropped and reported when its owner is absent; its column enumerates as an empty table and a keyed lookup returns the neutral, never a type's zero. A send to an absent owner is discarded at `submit` under `dropped{sender, command, absent_owner}` (R4, R12).
6. **Event-typed payload fields (N3).** Every `EventRef` slot (`cause`, and the payload fields the owner types `EventRef`) is rewritten at the merge; an integer there is `SimError::EventSlot` (R5, MIN-5).

**The spec side (this PR).** `[[reads]]`: `neutral` on every `rate` and `mode` read of another system's column, none on an identity read (R12); `[[owns]]` enum columns carry their codes (`values` by position, or `registry = "<table>"`); `[[applies]]` payloads are typed in a closed vocabulary (`PersonId`, `EventRef`, `SimTime`, the id types, `u8`..`u64`, `i64`, `bool`, `q8_8`, `q16_16`, `enum(<entity.column>)`; a `*_event` field is an `EventRef`; one entry per command) with `drained_by`, `key`, `key_field` and `outcome`; a sender's `[[commands]]` entry for an outcome command names its `timer` and `purpose` (R9). `lint_odd.py` checks all of it (enum membership, ranges, fixed-point representability, the coupling prose as `<column> = <value>`, a `sprint` escape that ends when the sprint's document is CLOSED: R13, NIT-8) with fixtures both ways; a wrong value is always an error, a missing declaration is an error on a frozen spec and a warning on a draft (ADR-0033's rule, with the stricter value check recorded as deliberate: MIN-2). M2 0.2.1, M7 0.3.2 and T1 0.3.2 carry the declarations; under R12 the P1b identity reads of S6 and S7 leave M7 and T1 until those specs are frozen, and M7's read of `person.named` becomes a mode read with `neutral = false` (a flag that switches dormancy), so both register in P1a; the lint prints, per spec, the owners its identity reads require (T1: M2 and M7; M7: M2), and refuses an identity read on a substrate (`role = "substrate"`, a system that must run alone, M2 on `solo`) of anything but another substrate's column (the Architect's R12 clarification; M2 0.2.1 reads nothing foreign, and the births draft carries M2's reads as rate or mode); the smoke specs declare what their code does today (`Settle` and `Audit`, `Day`/`Activity`, `key = "any"`, keyed by `person`).

## 3. How the text answers the brief

- **Ordering within the owner:** key order, led by the submission instant. Two commands sent in the same instant arrive in phase order, then by `PersonId`, then by merge order (the canonical level order), whatever the thread count.
- **An owner whose draining binding has run:** a request command waits in its queue (plane-A state) until that binding next runs; in P1a every sender submits at a day-start instant (every P1a binding is `Year`, `Month` or `Day`, all of which fire at day starts, and every timer fires at a day start since BLK-1) and every draining binding is `Day`, so a request waits at most one day (T1's `PressClaim` at `Agenda` d is applied at `Agenda` d + 1). An outcome-carrying command never waits: its sender's timer submits it in the outcome's instant. Minute-level senders are A-35.
- **The timer pass:** drains nothing, and it is where every outcome-carrying command is submitted: a command merged in the timer pass of phase *p* is in the inbox for the draining binding's run in the binding pass of *p* (M7's `MURDER_DUE` and T1's `DEATH_DUE` and `MARRY_DUE`, fired in `Vital`'s timer pass, are drained by M2's `Day`/`Vital` binding in the same `Vital`).
- **The level merge:** unchanged. The merge is the only writer of the queues and assigns `seq`; a command sees its cause's `EventId` because a system's events merge before its commands; an event-typed payload field is rewritten at the same point.
- **V-SAGA-19:** satisfied without delivery, by `apply_death` in `Vital` and M7's `same_instant` reads at `Polity` (BLK-1). What delivery adds in the death instant is the `PASSED_OVER` opinion and a newborn's promotion reaching T1 at `Agenda` of the same day.
- **The frozen specs' wording.** M7's and T1's `[[couplings]]` say a command is "applied at the next tick boundary"; under the rule that reads "at the owner's draining binding's next run", which for a `Polity` send to T1 is `Agenda` of the same instant and for an `Agenda` send to M7 or M2 is the next day start. M7's `[[couplings]]` line for T1's commands says so at 0.3.2; the rest of the prose is corrected when those specs next change.

**R6, ruled in round 2 as R9: shape (b), strengthened.** Both options as written for the ruling, with the four facts the Architect asked for; the ruling and the round-3 text follow.

*(a) A queued dated command is the scheduled outcome.* `ScheduleDeath` and `Marry` keep a `tick`; the draining binding applies a command dated at its instant and turns a later-dated one into a timer owned by the drainer. ADR-0025 item 3 is extended: in `Inputs`, pending timers **and queued commands** whose key person is in the scope are cancelled and re-sampled, the command by its sender through a new `resample_command` hook (the sender drew the date, so only it can re-draw). DET-13's "shall be a plane-A timer" is amended to "a timer or a dated lifecycle command". Facts: (1) a murder's death applies at the dated day start's `Vital`, in M2's drain (T1: d + 1; M7: the drawn day); (2) the sender re-draws, through `resample_command`, and after the drainer has converted the command into its own timer, the drainer would re-draw a date it never drew unless the timer records its origin; (3) M2's frozen `ScheduleDeath.tick` stays; (4) smoke: none (no smoke command is dated). Costs: a requirement and an ADR amendment (the director's), a second re-sampling path, and a queue indexed by entity for scope lookups. **M2's shape under (a)** (the Architect's addendum, 2026-10-17, and the births drafter, PR #50): the drain writes a later-dated command into an M2-owned plane-A table `pending.*` (kind, tick, the parties, cause, culprit, `cause_event`, sender; hashed, in keyframes, the row removed when applied) and inserts an M2 timer of kind `COMMANDED_DEATH` or `COMMANDED_MARRIAGE` at `(tick, Vital)` under a purpose `commanded` with `resample_on_fork = false`, whose `resample_timer` returns the same tick, so a scoped input leaves a commanded outcome where its sender put it and never re-draws it as a hazard death; the fire applies the row's cause and parties. Binding whatever R6 decides: a commanded outcome is never filed under a `resample_on_fork = true` purpose (M2's `death_time`) and never loses its cause fields.

*(b) No dated commands; a later outcome is its sender's timer (recommended, and ruled: R9).* A command carries no date. A sender whose outcome is due later holds a timer in the agenda at the outcome's `(day, phase)` and submits the command when it fires. The round-2 draft let a sender whose outcome was due at the drainer's next run "just submit"; the review's MAJ-6 showed that T1's next-day `ScheduleDeath` and `Marry` then crossed an `Inputs` phase as queued commands, outside ADR-0025 item 3, so R9 removed the carve-out: every outcome-carrying command is submitted by a timer, T1's included. DET-13 and ADR-0025 then stand as written. Facts: (1) a murder's death applies at the same instant as under (a): T1 sends at `Agenda` d and M2's `Day`/`Vital` drain applies it at d + 1 (MAJ-4's timing); M7's murder is an M7 timer at `(the drawn day, Vital)`, fired in `Vital`'s timer pass by a new `Day`/`Vital` binding of M7 (`murder_due`) that submits, and M2's drain applies it in that same `Vital`, before the bindings that read M2, so the death is dated the drawn day as before; (2) the sender re-draws its own timer through the existing `resample_timer`, keyed by its own purpose (`exit_murder`); no new path; (3) `tick` leaves M2's `ScheduleDeath` and `Marry` (0.2.1, a no-mechanics bump: nothing is built against 0.2.0's payloads) and the senders' `[[commands]]`; M7 gains a binding and a step; (4) smoke: none. Costs: M7's `Day`/`Vital` binding (an empty step on days with no timer; M7 is not built yet, so no code changes); T1's `Day`/`Vital` already exists, and T1 gains two timer kinds, `DEATH_DUE` and `MARRY_DUE`, under a new purpose `outcome_delay` whose `resample_timer` returns the timer's own tick (the one-day delay is not a draw). A timer must carry the `MURDER_ATTEMPT` that caused the death, so the engine gives a timer one `EventRef` slot (`cause`) rewritten at the merge, and the merge takes a system's events before its timers (rule 4; hash-neutral: the agenda's `seq` and the `EventId` are separate counters). M7's `MURDER_DUE` carries the culprit in its integer payload and is re-sampled under `exit_murder` (the day re-drawn among the month's remaining day starts; R10). **M2's shape under (b):** the drain applies every command it takes in that `Vital` and files nothing; there is no `tick` to check and no pending table. The addendum's binding rule holds by construction: the only timer behind a commanded outcome is the sender's, under the sender's own purpose (`exit_murder`, which M7 drew and M7 re-samples), and the cause fields travel in the command at fire time. The births drafter's objection to (b), that M7's timer would have to sit in `Vital`, "a phase M7 does not bind", or the death slips a day, is met by the `Day`/`Vital` binding M7 gains at 0.3.2 in this PR: the timer fires in `Vital`'s timer pass, which precedes every binding, and M2's drain runs in the binding pass of the same `Vital`. **No timing is lost**, so by R6 the Architect rules it; D39 records the choice for the director as part of the whole.

Recommendation: **(b)**, confidence **7/10**. The 3/10 against: (a) keeps "a command with a date" as a notion the specs already used (M2 0.2.0, M7 0.3.1, T1 0.3.1 all wrote `tick`), and (b) makes M7 bind a phase it has no other business in. The births drafter (PR #50) recommended (a) at 65% in round 2; the Architect ruled (b) strengthened (R9), and PR #50 switches to it: M2 files nothing, its `Day`/`Vital` drain applies every command it takes in that `Vital`, and its two commands are `outcome = true`. The review noted two within-instant orderings that differ from the frozen 0.3.1 text and that no golden world holds: a natural death and a murder of the same person on one day (the natural death, in M2's timer pass, now always comes first), and an M7 and a T1 murder of one victim on one day (both now arrive from timers in the same timer pass, M7's at M7's level before T1's, so the `DEATH` carries M7's culprit; `apply_death` drops the second).

## 5. Hash effect and class

This PR changes text, a lint and four specs: no golden hash moves (`bin/check_all.sh`, both parts). SPR-014's implementation is C3 by PRJ-002 (scheduler semantics), and the rule is written so that **no existing baseline moves**: the smoke world's commands keep flowing (`key = "any"`, `drained_by` naming the binding its code already drains in, no dated commands to convert), and `solo`, `household` and `hamlet` register M2 alone, send nothing and read nothing foreign; M2's new `Day`/`Vital` drain binding makes the engine run an instant at every day start that changes no column, draws nothing and emits nothing, so month-end hashes are expected equal. SPR-014 shows this with its ladder comparison and takes "the smoke ladder is unchanged" as an acceptance criterion (R1); a difference is a defect, not a `[C3]` regeneration. SPR-014 also emits each spec's `drained_by` bindings into the generated skeleton and compares them at registration, as `SCHEDULE` is compared, so a spec cannot name a binding its code does not drain (NIT-10). The first world whose history depends on delivery order is the dynastic fixture (SPR-021, SPR-030), whose baseline is recorded after this text. The withdrawn G5 refusal changes registration reports only.
